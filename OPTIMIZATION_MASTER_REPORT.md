# Сводный отчёт по оптимизациям движка

Состояние: исходный интеграционный кандидат на базе `wip/providers-2026-09-23` и `codex/architecture-tradeoffs` уже вошёл в `main`; обе ветки Dependabot также учтены в его истории. Ниже сохранена исходная оценка, а в конце добавлено измерение последующей оптимизации стриминга.

## Что вошло в кандидат

- Перенос модулей и provider-интерфейсов из `wip/providers-2026-09-23`.
- Оптимизации раундов 1–2 по world/physics, audio, render, content, media, numeric, modding и task pool; вместе с ними — регрессионные тесты и ручные A/B-бенчмарки.
- Раунд 3: хранение backend в заголовке объекта рендера, компактный порядок загрузки модов и однопроходное перечисление контент-каталога через компактный staging-буфер.
- Ветка Dependabot `actions/checkout` объединена; в актуальном workflow уже используется тот же SHA `3d3c42e5…` для v7.0.1.
- Ветка Dependabot `actions/download-artifact` объединена в истории. Её workflow основан на устаревшей структуре CI; актуальный workflow не скачивает artifacts, поэтому SHA v8.0.1 там пока негде использовать. Старые jobs из этой ветки не возвращались.

Стенд теперь устанавливает сервис явно, считает ошибки ошибкой процесса и печатает ненулевые контрольные суммы.

## Интеграция и исправления

- Git обнаружил девять содержательных конфликтов. В разрешении сохранены provider-границы `wip`: аудиомодуль получает контент только через таблицу сервиса, renderer оставляет provider-файлы и переносит `renderer_internal.h` в новое расположение, world batch освобождает память через allocator самого мира.
- Переписаны устаревшие пути к исходникам в CMake после переезда `src/render`, `src/physics` и `src/media`.
- DDA- и UI-тесты подключены к новым публичным интерфейсам. Тест звукового PCM16 обращается к загрузчику через таблицу сервиса; тесты world, panorama и texture pack явно устанавливают необходимые providers.
- Исправлена проверка optional graphics module: headless-тест теперь выбирает offscreen Vulkan, а не оконный D3D12 через AUTO.
- При слиянии веток Dependabot сохранён актуальный workflow из интегрируемой архитектурной ветки, а не возвращены старые jobs упаковки, которые расходятся с новым набором CMake presets. Используемый checkout SHA уже совпадал с версией v7.0.1 из Dependabot; `download-artifact` в актуальном workflow не вызывается.

## Решение перед публикацией

Оптимизацию мира оставил: после восстановления корректной работы benchmark provider setup замедление одиночной записи не подтвердилось, а повторные измерения показали ускорение одиночного сценария примерно на 66.5% и пакетных сценариев на 94.0–97.4%. Компактный каталог тоже оставлен: он уменьшает пик памяти примерно на 29% и сокращает общее время набора сценариев в 8 из 9 пар; цена — лишь 8–27 мкс на перечислении очень маленького каталога из 64 файлов. Release/Debug CTest кандидата прошли 71/71.

## Последующее измерение: очередь стриминга чанков

- `QueueChunkIfMissing` теперь объединяет поиск и вставку в один проход открытой адресации. Если запись уже есть, она возвращается; если ключа нет, первый пустой слот сразу заполняется. Раньше сначала выполнялся `FindEntry`, а затем отдельный `InsertEntry`, то есть отсутствующий чанк проходил цепочку пробирования дважды.
- A/B сравнение против `HEAD eebc212` выполнено на Windows x64/MSVC Release. Для каждого варианта запущено по три полных прохода standalone `laiue_streaming_benchmark`, радиус 12, 200 шагов; сравнивается медиана времени `SetCenter` на вызов.

| Сценарий | База, мкс/вызов | Изменение, мкс/вызов | Снижение времени |
|---|---:|---:|---:|
| worker sleep 0 мс | 83.599 | 73.399 | 12.2% |
| worker sleep 8 мс | 155.300 | 139.800 | 10.0% |

Это выигрыш именно в микробенчмарке смены центра, а не измерение FPS игры. Для этой правки расход памяти отдельно не замерялся; алгоритм не добавляет таблиц или постоянного состояния. Добавлен тест повторной установки того же центра: он проверяет, что заявки и эпоха центра не меняются; тест стриминга прошёл в Release и Debug.

Новый module-host benchmark теперь вычисляет измерение и checksum последовательно; это исправило дефект порядка вычисления аргументов, пойманный независимым аудитом. Ревью не нашло других actionable-дефектов в библиотечном коде или остальных benchmark-изменениях.

### Кандидаты, которые не перенесены

- Увеличение lookahead rigid solver с 8 до 32 ухудшило медиану примерно на 0.36% для solver и на 0.74% для полного шага; production-константа оставлена прежней.
- Эксперименты с production chunk mesher не дали устойчивого выигрыша, поэтому изменён только harness.
- Alpha fast path в resampler из отдельной старой ветки дал в сумме сценариев лишь около 1.05% выигрыша, но замедлил zero-alpha сценарии на 7.1–7.6% и один sparse-alpha сценарий на 4.9%; он отклонён, поскольку результат заметно зависит от распределения альфы и памяти не экономит.

### Проверки интеграции

- Visual Studio 2026 / MSVC, CMake preset `windows-msvc`: полная Release-сборка и CTest **71/71**; полная Debug-сборка и CTest **71/71**.
- Отдельно собраны mesher, world batch, module host и оба rigid-body benchmark-targets. Module-host, world dense/sparse, mesher mixed и оба rigid-body benchmark smoke-запуска завершились с кодом 0.
- `git diff --check` прошёл. GitHub CI будет проверен после отправки коммита.

## Раунд 19: компактная арена перестройки чанков, 2026-09-27

При смене мирового origin таблица чанков перестраивается через временную арену. Её строки раньше имели полный размер `ChunkEntry` — 48 B на x64, включая revision, состояние и номер элемента списка отрисовки, которые при переносе не используются. Новый приватный `ChunkRebuildEntry` хранит только три координаты и указатель на меш (32 B). Размер основной таблицы и публичный ABI не меняются; код обхода и порядок операций сохранены.

Арена заранее выделена на `(2R+3)^3` строк, поэтому экономия составляет ровно **16 B × (2R+3)^3**. При радиусе 12 это **314,928 B (307.5 КиБ)**; при радиусе 16 — **686,000 B (669.9 КиБ)**. В этой же пропорции уменьшается объём копирования сохранённых мешей во время редкой перестройки origin. Отдельного замера времени для этой редкой операции не делал; дополнительной работы в обычном кадре нет.

Тест стресс-потока теперь детерминированно проводит живые меши через арену сменой origin с нулевым смещением и проверяет сохранение записей списка отрисовки, затем выполняет существующие случайные origin-переходы.

## Раунд 22: пропуск нулевого вращения и объединение Vulkan-загрузок, 2026-09-27

### Physics: пропуск преобразования нулевой угловой скорости

Пять чередующихся пар отдельных Release x64 MSVC процессов. В каждом процессе benchmark брал пять выборок по восемь физических шагов (после двух шагов прогрева), затем мы сравнивали медианы пяти process medians:

### Vulkan: пакетная запись копирования геометрии

Последовательные загрузки с общими staging и destination буферами теперь записываются одним vkCmdCopyBuffer с несколькими регионами. Диапазоны source кольца выдаются монотонно, destination-диапазоны удерживаются пулом; эта гарантия устраняет перекрытия, поэтому лишняя квадратичная проверка диапазонов не выполняется. Сохраняются исходный порядок загрузок, учёт каждого байта, отложенное освобождение собственных staging-буферов и общий transfer-to-vertex barrier. Scratch-массив из 64 VkBufferCopy занимает около **1.5 КиБ стека** только на время записи кадра; heap и постоянная память не увеличились. Vulkan API и public ABI не менялись.

Пять чередующихся пар Release x64 MSVC процессов, каждый с пятью внутренними выборками. В r2_21_vulkan_submit_benchmark измерялся сценарий upload64_frame: 64 меша на кадр, 1000 кадров на выборку. Медиана process medians снизилась с **43.557 до 43.130 мс** (**−0.98% времени**). Первая версия с квадратичной проверкой перекрытий дала −0.26% (по сути паритет); после проверки инвариантов allocator эта проверка убрана, и финальная версия дала небольшой устойчивый выигрыш. Контрольный framebuffer checksum 14413869a0290d83, количество draws, quads и uploaded bytes совпали во всех baseline/candidate запусках. Отдельный offscreen-тест проверяет точный счётчик байтов, все 64 draw и центр каждой из 64 ячеек.

Отдельный, существовавший до этого изменения риск жизненного цикла: RendererCreateMesh записывает данные в staging ring текущего frame-slot до вызова RendererBeginFrame, а fence этого слота ожидается уже внутри RendererBeginFrame. При повторном использовании слота CPU поэтому может записать staging-память, пока предыдущий GPU submit ещё работает. Пакетирование сохраняет тот же порядок и не исправляет этот риск; offscreen-тест проверяет содержимое пачки, но не многокадровую гонку. Это требует отдельного решения синхронизации staging-записей.
