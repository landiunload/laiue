# Удешевление хвоста таблицы кадров анимации

Отчёт о правке `TexturePackFillSliceTable` (`src/render/texture_pack.c`).
Изменён только один файл движка; CMake, публичный API, оба бэкенда и
тестовые цели не тронуты. Всё измерительное и проверочное лежит в
`build/peer/` — это не часть дерева исходников.

## 1. Что и чем измерено

Функция `TexturePackFillSliceTable` **не экспортируется** из
`laiue_render.dll` (проверено `dumpbin /exports`: наружу идут только
`TexturePackActivate/ActivateIn/Enumerate/EnumerateFrom/ListRelease`).
Поэтому из `tests/render_pack_api_test.c` её не вызвать без новых
экспортов, а новые экспорты запрещены. Проверка сделана отдельным стендом
`build/peer/texpack_profile.c`, который компилирует **настоящий**
`src/render/texture_pack.c` (и, для A/B, сохранённую копию прежней
редакции `build/peer/texture_pack_before.c`) и линкует их против
`laiue_content` + `laiue_platform_support`.

Сборка стендов (`build/peer/build_ab.bat`) идёт с флагами, совпадающими с
Release-сборкой движка: `/O2 /Ob3 /GL` и линковка `/LTCG`. Иначе решение
компилятора об инлайне `TexturePackResolveSlice` менялось и числа A/B
плыли (это видно в разделе 6).

Стенд делает три вещи:

1. **Побайтное равенство.** Для каждого набора считает `outSlices` прежней
   реализацией (`ReferenceFillSliceTable`, дословная копия старой функции
   из `git show HEAD:src/render/texture_pack.c`) и текущей, сравнивает все
   16 слов.
2. **Цена одного `TexturePackResolveSlice`.** Отдельный вызов из другого
   модуля трансляции, минимум из 40 серий по 20 000 итераций.
3. **Цена всего перебора 64 слотов.** `TexturePackFillSliceTable` целиком,
   минимум из 60 серий по 20 000 итераций.

Наборы: `materialCount` = 1, 8, 32, 64; статичные (`frameCount = 1`) и
анимированные (`frameCount` = 64/16/8/4, чтобы уложиться в 256 слоёв).
«До» и «после» — это два разных процесса, которые запускаются вперемешку
(8 раундов), из серии берётся минимум. Это отделяет правку от дрейфа
загрузки общей с другими агентами машины.

## 2. Что найдено чтением кода и дизассемблера

`TEXTURE_PACK_MAX_LAYERS` = 64, цикл всегда делает 64 итерации. Для
`material >= materialCount` подставляется `source = materialCount - 1`, то
есть готовый кадр последнего материала. Прежняя редакция решала его
заново на **каждом** слоте-заглушке.

`dumpbin /disasm` по `texture_pack.obj` показал, что `TexturePackResolveSlice`
инлайнится в `TexturePackFillSliceTable`, но повторные вызовы для одного и
того же `source` **не** сворачиваются общим подвыражением: в теле цикла
стоят полные копии вычисления кадра (включая `divsd`). То есть лишняя
работа реальна, а не оптимизируется компилятором.

## 3. Что изменено

Было (суть):

```c
for (material = 0; material < TEXTURE_PACK_MAX_LAYERS; ++material)
{
    source = material < materialCount ? material : materialCount - 1u;
    slice = TexturePackResolveSlice(set, source, animationSeconds);
    ...
}
```

Стало:

```c
uint32_t slice = 0u;
for (material = 0; material < TEXTURE_PACK_MAX_LAYERS; ++material)
{
    if (material < materialCount)
        slice = TexturePackResolveSlice(set, material, animationSeconds);
    // для хвоста slice уже равен кадру последнего материала
    packed = slice > 255u ? 255u : slice;
    outSlices[material >> 2] |= packed << ((material & 3u) * 8u);
}
```

Форма с одним фиксированным проходом выбрана намеренно: она сохраняет один
сайт вызова `TexturePackResolveSlice`, который компилятор инлайнит. Вариант
с двумя отдельными циклами ломал инлайнинг (раздел 6).

**Почему выход побитово тот же.** Для `material < materialCount` в оба
варианта пишется `clamp(resolve(material))`. Для `material >= materialCount`
в старом коде писался `clamp(resolve(materialCount - 1))`, а в новом в
`slice` уже сохранён ровно `resolve(materialCount - 1)` (последний
присвоенный в основном проходе), и в байт пишется `clamp(slice)`. `clamp`
(насыщение к 255) применён и к хвосту, как раньше. `materialCount == 0`
обработан ранним `return` до цикла. Разбиение по словам
(`outSlices[material >> 2] |= slice << ((material & 3u) * 8u)`) не
изменилось, сдвиги в одном слове не пересекаются, порядок записи на
результат не влияет.

## 4. Результат: таблица до/после по размерам пака

Минимум из 8 перекрёстных прогонов, флаги движка (`/O2 /Ob3 /GL /LTCG`).
Время — на один вызов `TexturePackFillSliceTable`, наносекунды.

| materialCount | тип | frameCount | до, нс | после, нс | ускорение |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | статичный | 1 | 48,29 | 39,03 | **1,24×** |
| 8 | статичный | 1 | 48,30 | 40,06 | **1,21×** |
| 32 | статичный | 1 | 48,29 | 43,73 | **1,10×** |
| 64 | статичный | 1 | 48,29 | 48,91 | 0,99× (пар) |
| 1 | анимированный | 64 | 168,39 | 41,06 | **4,10×** |
| 8 | анимированный | 16 | 169,67 | 52,59 | **3,23×** |
| 32 | анимированный | 8 | 168,31 | 94,65 | **1,78×** |
| 64 | анимированный | 4 | 168,39 | 150,14 | **1,12×** |

Разделение цены (до правки):

- один вызов `TexturePackResolveSlice` (вне инлайна, из другого TU):
  статичный — **0,62 нс**, анимированный — **2,28 нс**;
- весь перебор 64 слотов: статичный — **48,3 нс**, анимированный —
  **168,4 нс**. Поскольку `TexturePackResolveSlice` внутри инлайнится, на
  слот с упаковкой выходит ≈0,75 нс (статичный) и ≈2,6 нс
  (анимированный). Отсюда и выигрыш: у анимированных материалов именно
  повторное решение кадра доминировало, а его убрали.

Пункт 3 задачи подтверждён: при `materialCount`, близком к 64, хвоста нет,
и выигрыша нет — статичный 64 остаётся на уровне «до» (0,99×, разница
0,6 нс — в пределах шума). Небольшое ускорение анимированного 64 (1,12×)
обязано раскладке кода (упростился выбор `source`), а не меньшему числу
решений, и как выигрыш алгоритма не заявляется.

## 5. Что проверено

- **Побайтное равенство `outSlices`.** Сравниваются все 16 слов, наборы:
  `materialCount` = 0, 1, 2, 63, 64, 65, 67; `frameCount` = 1…5; статичные
  и анимированные; время `0`, отрицательное, `1e-9`, `0.001234`, `0.999`,
  `1`, `1234.5`, `±1e9`. Плюс 4000 случайных наборов (`materialCount`
  0…67, `frameCount` 1…6, случайный `firstSlice` вплоть до 399, случайные
  длительности, в том числе нулевые) и `set == NULL`. Итог каждого прогона:
  `equivalence failures=0`, `MISMATCH` отсутствует (16/16 прогонов A/B).
- **Полная сборка и тесты.** `cmake --build --preset windows-msvc-release
  --parallel 4` — без предупреждений (они ошибки), проверка границ
  архитектуры `OK (104 files)`; `ctest --preset windows-msvc-release
  --no-tests=error` — **30/30**.
- **Фальсификация.** В `TexturePackFillSliceTable` намеренно размножен не
  тот слот: хвост получал кадр материала 0 вместо `materialCount - 1`.
  Стенд поймал: `equivalence failures=3819`, в том числе
  `MISMATCH count=2 ...`, `MISMATCH random seed=1 count=8 ...`. Правка
  откачена, повторная проверка — снова `0`.

## 6. Что рассмотрено и отклонено (с цифрами)

- **Два цикла: `materialCount` решений, затем хвост готовым значением.**
  Именно это ближе всего к формулировке задачи, но при `materialCount == 64`
  проход становится с переменным числом итераций, и `TexturePackResolveSlice`
  теряет инлайн. Измерено: `materialCount=64`, статичный — **55,6 нс
  (0,87×)**, то есть регресс; анимированный — 162 нс (1,05×). Вариант
  с одним фиксированным проходом (принят) даёт на том же входе 48,9 нс
  (0,99×). Отклонено.
- **Явная ветка `materialCount == 64` со старым циклом + общий путь.**
  Два места вызова `TexturePackResolveSlice` → компилятор перестаёт
  инлайнить, появляется настоящий `call`. Измерено: `materialCount=64`
  статичный — **95,6 нс (0,50×)**, анимированный — 217 нс (0,79×).
  Отклонено.
- **Специальный случай «нет анимированных материалов вовсе».**
  Результат тогда не зависит от времени, но всё равно зависит от
  содержимого пака, и без кэша между кадрами (запрещён) его пришлось бы
  считать целиком. Кэш таблицы уже пробовали в
  `docs/render_ring_parallel_work.md` (раздел 6) — выигрыш ниже шума,
  откатили. Повторно не вводился.

## 7. Про безусловность вызова (пункт 4)

- **D3D12.** Вызов (`renderer_d3d12.c:2304`) стоит **после** раннего
  `return true` при `frame->passCount == 0` (`:2252–2272`). То есть при
  кадре без проходов сцены функция уже не вызывается. Безусловным вызов
  является только для кадров с проходами.
- **Vulkan.** Вызов (`renderer_vulkan.c:2076`) стоит **до** ветки
  `frame->passCount == 0` (`:2081`), то есть зовётся на каждом успешном
  `RendererBeginFrame`, даже когда проходов нет.
- **Можно ли не звать вовсе.** Безопасного пути без состояния между
  кадрами нет. Пропуск по «`animationSeconds` не изменился» или «в паке
  нет анимации» требует кэша времени/результата, а глобальные и
  потоко-локальные кэши запрещены. Перенос вызова за ветку
  `passCount == 0` в Vulkan — это изменение остальной логики
  `BeginFrame`, что зоной задачи запрещено (менять можно только аргументы
  вызова). Поэтому в этой части ничего не сделано; уже существующий
  пропуск на D3D12 лишь зафиксирован.

## 8. Воспроизведение

```bat
build\peer\setup.bat
build\peer\build_ab.bat
rem запускать вперемешку, минимум из серии:
build\windows-msvc\bin\Release\texpack_profile_before.exe
build\windows-msvc\bin\Release\texpack_profile_after.exe
```

`texpack_profile_before.exe` собран из `build/peer/texture_pack_before.c`
(копия `HEAD`), `texpack_profile_after.exe` — из текущего
`src/render/texture_pack.c`. Полная сборка и тесты:

```bat
cmake --build --preset windows-msvc-release --parallel 4
ctest --preset windows-msvc-release --no-tests=error
```
