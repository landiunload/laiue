# Путь вывода WASAPI: разбор, расхождение по моно и отказ от микроправок

Работа велась в изолированном дереве `C:\Users\landi\projects\laiue-wasapi`,
ветка `peer/wasapi`. Зона — только
[src/audio/audio_wasapi.c](../src/audio/audio_wasapi.c); микшер
(`audio_mixer.c`), публичный `audio.h` и CMake не трогались. Публичный API,
ABI, экспорты и раскладка клипа не менялись.

Итог короткий. В горячем цикле вывода нет ни лишних системных вызовов, ни
работы, которую можно было бы посчитать один раз при инициализации, ни
аллокаций и блокировок между `GetBuffer` и `ReleaseBuffer`. Единственное
расхождение — **моно-устройство**: до правки правый канал микса полностью
отбрасывался (звук, запанорамированный вправо, пропадал). Это исправлено
сложением каналов с половинным масштабом; стерео и многоканальный пути
доказанно не изменились. Измеримой оптимизации горячего пути не нашлось:
общая (стерео) раскладка и так `memcpy`, а её цена на устройстве этой машины
— доли наносекунды против периода в 22 мс.

## 1. Разбор `RenderThreadEntry`

Путь один к одному: `CoInitializeEx` → `CoCreateInstance` перечислителя →
`GetDefaultAudioEndpoint` → `Activate(IAudioClient)` → `GetMixFormat` →
проверка формата → `Initialize` (общий режим, `EVENTCALLBACK`, период по
умолчанию) → `SetEventHandle` → `GetBufferSize` → `GetService(IAudioRenderClient)`
→ выделение `mixFrames` → `Start` → `AvSetMmThreadCharacteristicsW`.

Горячий цикл (`audio_wasapi.c:195`–`:218`):

```
WaitForSingleObject(bufferEvent, 2000)   // один раз
GetCurrentPadding                        // один раз
available = bufferFrameCount - padding
GetBuffer(available)                     // один раз
render(context, mixFrames, available)    // микшер, не трогается
SpreadStereoToDevice(...)                // раскладка
ReleaseBuffer(available, 0)              // один раз
```

Что проверено по пунктам задания:

- **Лишних системных вызовов нет.** `GetCurrentPadding`, `GetBuffer` и
  `ReleaseBuffer` вызываются ровно по одному разу за итерацию.
  `IAudioClient_GetService` — один раз при инициализации, полученная ссылка
  отпускается один раз в `cleanup`. В цикле нет ни `AddRef`, ни `Release`.
- **Формат не пересчитывается на каждый буфер.** `FormatIsFloat32` и проверка
  каналов выполняются один раз, до `Start`. Общий режим означает, что
  устройство уже работает на своей частоте, поэтому в цикле нет ни
  ресемплинга, ни конвертации сэмплов. Единственное решение на буфер —
  предсказуемая ветка `SpreadStereoToDevice` по постоянному
  `deviceChannelCount`.
- **Аллокаций и блокировок между `GetBuffer` и `ReleaseBuffer` нет.**
  `mixFrames` выделяется один раз при инициализации; в интервале работает
  только микшер и чистая раскладка. `backend->render` по контракту
  (`audio_backend.h:13`) блокирующих операций не делает.
- Поле `mixFrameCapacity` записывается, но нигде не читается — безвредный
  остаток, к оптимизации отношения не имеет.

## 2. Число каналов: что реально происходит

Проверка `mixFormat->nChannels == 0u` есть (`audio_wasapi.c:163`), а
`FormatIsFloat32` синтетически прогнан на пяти заголовках (см. стенд):

| заголовок | принимается |
| --- | --- |
| PCM16 | нет |
| IEEE float32 | да |
| PCM32 | нет |
| EXTENSIBLE + IEEE float | да |
| EXTENSIBLE + PCM | нет |
| EXTENSIBLE с коротким `cbSize` | нет |

Раскладка микса (всегда стерео, `AUDIO_MIX_CHANNELS = 2`) в кадр устройства:

- **`nChannels == 2`** — точный `memcpy`; на реальном устройстве этой машины
  формат именно такой (`EXTENSIBLE`, 2 канала, 48 кГц, 32-битный float,
  `nBlockAlign = 8`, буфер 1056 кадров ≈ 22 мс).
- **`nChannels > 2`** — весь буфер обнуляется, левый/правый кладутся в первые
  два канала, остальные молчат. Это ровно то, что записано в комментарии
  (`audio_wasapi.c:97`), выхода за границы нет: максимальный индекс
  `(frameCount-1)*nChannels + 1 < frameCount*nChannels`. **Это не баг, а
  осознанная политика**: движок не разносит стерео по 5.1 сам. Проверено
  побайтово на 4/6/8 каналах.
- **`nChannels == 1`** — вот здесь расхождение. Старый код считал
  `copied = 1` и писал в моно только **левый** канал. Всё, что микшер
  запанорамировал вправо (вклад `right` в
  `audio_mixer.c:471`–:472), исчезало. Это не порча памяти и не шум, а
  **потеря половины сигнала**: для источника, стоящего справа, на
  моно-устройстве наступала тишина. Именно этот случай задание и просило
  проверить.

Воспроизведение (стенд, кадры `L=0,R=1` и `L=1,R=0`, до правки):
`mono right-only -> 0, left-only -> 1`. После правки:
`mono right-only=0.5 left-only=0.5 centered=0.5 full=1`.

### Что изменено

В `SpreadStereoToDevice` добавлена ветка `nChannels == 1`: каналы
складываются с половинным масштабом `(L + R) * 0.5f`. Половинный масштаб, а
не просто сумма: микшер уже ограничивает каждый канал в `[-1, 1]`
(`audio_mixer.c:512`), и сумма без масштаба вылезла бы за диапазон. Это
исправление корректности, а не оптимизация; ветки стерео и `nChannels > 2`
не тронуты, поэтому их выход обязан остаться прежним — и остался.

## 3. Стенд и измерения

Стенды лежат только в `build/peer/` (каталог вне индекса, в поставку не
входит):

| файл | что делает |
| --- | --- |
| `wasapi_spread_probe.c` | подключает `audio_wasapi.c` как исходник (как `audio_alloc_probe` для микшера) и вызывает **настоящие** статические `SpreadStereoToDevice`/`FormatIsFloat32`; проверяет раскладку побайтово, печатает хеши и время, а также формат реального устройства |
| `wasapi_probe_build.bat` | собирает стенд `cl /O2 /W4 /WX /fp:fast /arch:AVX2` |
| `wasapi_build.bat` | пересборка Release-дерева движка (не более 4 потоков) |

Методика дня: сначала побитовое сравнение с эталоном, потом время (минимум
из 7 серий). Тесты и сборка — как в задании.

### 3.1 Побитовое совпадение с эталоном

Выход `SpreadStereoToDevice` сравнивался с независимой эталонной записью на
кадрах 1, 3, 480, 961 и каналах 1, 2, 4, 6, 8. **Все 20 сочетаний — `yes`**
как до, так и после правки. Хеши FNV-1a для стерео и многоканала не
изменились, например `channels=2 frames=480 → 28423050`,
`channels=6 frames=480 → cd100ad0`, `channels=8 frames=480 → deb12610`;
изменились только моно-хеши (`channels=1 frames=480: 204b8430 → 67028bc6`).

### 3.2 Время, нс на вызов (минимум из 7 серий)

| каналов | 64 | 480 | 960 | 1920 | 4800 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2 (горячий, `memcpy`) | 5 | 26 | 50 | 127 | 557 |
| `memcpy` как контроль | 4 | 25 | 50 | 132 | 534 |
| 1 до правки (копия левого) | 44 | 313 | 624 | 1393 | 3722 |
| 1 после правки (сложение) | 18 | 127 | 250 | 555 | 1312 |
| 6 до/после | 71/69 | 575/501 | 1138/998 | 2965/2902 | 6577/6407 |
| 8 до/после | 75/69 | 606/521 | 1228/1070 | 2570/2612 | 6374/5734 |

Читается так: стерео-путь — это буквально `memcpy`, то есть минимум
возможного; многоканальный путь не изменился в пределах шума; моно-путь от
правки **подешевел** в 2.4–2.8 раза (исчез вложенный цикл со счётчиком
`copied`), но это побочный эффект, а не цель.

### 3.3 Цена в контексте реального устройства

Устройство этой машины — стерео, буфер 1056 кадров (22 мс звука при 48 кГц).
Экстраполяция даёт ≈ 57 нс на раскладку буфера — около **0.00026 %** этой
длительности. Даже микшер с одним голосом стоит ~0.6 мкс на 480 кадров, то
есть на порядок-два больше. Оптимизировать здесь нечего.

## 4. Рассмотренные и отклонённые правки

1. **Рендерить прямо в буфер устройства, без `mixFrames`, для стерео.**
   Убирает один `memcpy` на буфер. Выигрыш равен ровно цене раскладки:
   ~57 нс на буфер 1056 кадров (22 мс звука), то есть 0.00026 %.
   На фоне 0.05–0.15 мс микшера при 128 голосах это шум; вдобавок ветка
   усложняет цикл ради случая, который надо оставить отдельно для
   многоканала. Отклонено по правилу «без подтверждённого выигрыша — не
   оставлять».
2. **Векторизовать/развернуть многоканальную раскладку.** `nChannels > 2` на
   реальном устройстве не встречается (здесь — стерео), а абсолютная цена и
   так ниже микросекунды (`<0.6 мкс` на 480 кадрах). Отклонено.
3. **Убрать `copied`/вложенный цикл в многоканальной ветке** (после ранних
   выходов для 1 и 2 каналов в нём всегда `copied == 2`). Выход тот же,
   разница в пределах шума — чистая косметика, не оптимизация. Отклонено.
4. **Удалить нечитаемое поле `mixFrameCapacity`.** Безвредно, но это не
   удешевление пути. Отмечено, не менялось.

  `laiue.audio.system_backend` (последний на этой машине нашёл живое

  ветки не задевает (ранний `return` для моно стоит после стерео).
- Публичный API/ABI не менялся, новых экспортов нет; изменена только
  статическая функция внутри `audio_wasapi.c`.

Фальсификация (правка временно вносилась и откатывалась):

| намеренная поломка | что поймало |
| --- | --- |
| моно-масштаб `0.5f` заменён на `2.0f` | `channels=1 spread==reference=NO` (все размеры буфера) |

После возврата — снова все `yes`, моно `right-only=0.5`, 30/30. Действующее
покрытие CTest эту функцию не трогает напрямую (системный тест беззвучен и
идёт на стерео-устройстве), поэтому роль детектора выполняет стенд; в отчёте
это указано честно.

## 6. Что осталось непроверенным

- Моно-устройства на этой машине нет (реальный формат — стерео), поэтому
  моно-ветка проверена прямым вызовом `SpreadStereoToDevice`, а не живым
  выводом. Логика ветки — чистая арифметика над двумя `float`, стенд
  сравнивает её с независимым эталоном побайтово.
- Специфическая для 5.1 раскладка реального устройства не проверялась
  (устройства нет); подтверждено лишь отсутствие выхода за границы и
  побайтовое совпадение с задокументированной политикой.
- ARM64, clang и Linux-профили не запускались; правка не содержит ни SIMD,
  ни платформенных вызовов.
