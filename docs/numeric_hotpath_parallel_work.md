# Горячий путь арифметики произвольной точности: замер, лист на один лимб

Затронуты [src/numeric/infinite_coord.c](../src/numeric/infinite_coord.c) и
[tests/infinite_coord_test.c](../tests/infinite_coord_test.c). Публичный
`infinite_coord.h`, ABI, форма числа и поведение на нуле, отрицательных,
переносах между лимбами и границе `int64` не менялись. Ни глобальных, ни
TLS-кэшей не добавлено: вся правка — это ветвление и порядок вычислений,
куча по-прежнему только через `PlatformAllocate`/`PlatformFree`.

## 1. Сначала замер, а не догадка

Отдельный зонд (временный, вне дерева) собирается из текста
`infinite_coord.c` одним модулем трансляции. Перед включением исходника
подменяются имена платформенного аллокатора:

```c
#define PlatformAllocate InstrAllocate
#define PlatformReallocate InstrReallocate
#define PlatformFree InstrFree
#include ".../src/numeric/infinite_coord.c"
#undef PlatformAllocate
#undef PlatformReallocate
#undef PlatformFree
```

Обёртки считают вызовы, выделения, перевыделения и освобождения и
приписывают их тому входу, который выставлен в глобальной переменной перед
вызовом. Параллельно записывается распределение длины в лимбах. Нагрузка —
тикающая физика (512 тел, три оси, 64 тика) плюс парные вызовы по каждому
входу на одном и четырёх лимбах.

Детерминированные счётчики (не шумят, воспроизводятся бит в бит):

| вход | вызовов | alloc | realloc | free | лимбы 0/1/4 |
| --- | --- | --- | --- | --- | --- |
| `TryAddInt64InPlace` (тик) | 294 912 | **0** | 0 | 0 | 0 / 294 912 / 0 |
| `TryCopyAddInt64` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TrySetFromDouble` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryCopyShiftRight` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryCopyShiftLeft` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryAdd` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryCopyNegate` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryCopyMultiplyInt64` | 128 | 128 | 0 | 128 | 0 / 64 / 64 |
| `TryCopySquareAddInt64` | 128 | 256 | 0 | 256 | 0 / 64 / 64 |

Что из этого следует:

- Накопление на месте в обычном тике физики **вообще не ходит в кучу**:
  перенос из лимба и обнуление на такой нагрузке не встречаются, а нулевой
  старт — это одно выделение, которое потом живёт.
- Каждая операция, порождающая собственный результат, стоит ровно одно
  выделение и одно освобождение, а возведение в квадрат — два. Это уже
  минимум для публичной структуры, где `limbs` — указатель, а собственного
  буфера в структуре нет.
- Значит, дорогое здесь — не «сложение вообще», а **стоимость самого вызова**
  на однолимбовом беспереносном пути. Именно туда физика уходит девять раз на
  тело за шаг, и именно там скрывался выигрыш.

Микробенчмарк [benchmarks/numeric_physics_benchmark.c](../benchmarks/numeric_physics_benchmark.c)
меряет стоимость тех же входов до/после; он не менялся и остался тем же
инструментом A/B.

## 2. Что изменено

### 2.1 `TryAddInt64InPlace`: однолимбовый случай стал листом

Прежняя функция для любого входа сохраняла регистры и звала
`CompareMagnitudeSmall`/`SubtractMagnitudeSmall`/`Normalize` (на однолимбовом
значении это пара инструкций плюс пролог на каждый вызов). Теперь:

- канонический ноль (`limbCount == 0`) заводит лимб прямо на месте — без
  отдельного вызова;
- при `limbCount == 1` сложение с тем же знаком без переноса, вычитание
  меньшего, смена знака и точное погашение обрабатываются прямо в теле
  функции; на этом пути нет ни обращений к куче, ни вызовов, поэтому
  компилятор не генерирует пролог с сохранением регистров, а сам путь
  заканчивается `ret`ом;
- всё остальное (перенос из старшего лимба, многолимбовые величины,
  сравнение модулей) уходит в отдельную `noinline`-функцию
  `InfiniteCoordTryAddInt64InPlaceWide`. Она холодная и в горячий код не
  встраивается.

Порядок ветвлений подобран так, чтобы физически частый случай шёл по
кратчайшему пути. Поведение дословно прежнее: сумма, заём, знак, канонический
ноль, транзакционность при отказе выделения — всё то же.

`add_in_place.small`: **3.02 → 1.86 нс на операцию, −38 %.**

### 2.2 `InfiniteCoordToDoubleSaturating`: один лимб переводится без битового индекса

Для однолимбового значения `HighestSetBit` не нужен вовсе: `bitLength` заведомо
не больше 64, насыщения быть не может, и результат — это просто `(double)limb`
со знаком. Раньше поиск старшего бита всё равно исполнялся. Добавлен ранний
выход для `limbCount == 1`; для двух и более лимбов логика прежняя побитово.

`to_double.small`: **1.91 → 1.33 нс, −31 %.**

### Про широкий путь честно

`add_in_place.wide` в микробенчмарке подрос примерно на 10–16 %. Это цена
одной дополнительной проверки `limbCount == 1` на четырёхлимбовом входе;
отдельный замер только широкого накопления через настоящую DLL даёт
**2.955 → 3.162 нс (+7 %)**. Абсолютная величина — две десятых наносекунды, и
широкий путь на осевшей сцене не исполняется вовсе: по замеренной фактуре
физика уходит туда только когда добавка не помещается в `int64`. Обмен
сознательный: минус 1.16 нс на девяти вызовах на тело против плюс 0.2 нс на
редком пути. Обе цифры приведены, скрывать тут нечего.

## 4. Проверка

### 4.1 Независимый эталон, а не сравнение с собой

В `infinite_coord_test.c` добавлена модель целого со знаком
`ReferenceInteger`: модуль хранится **тридцатидвухбитными** цифрами
(база 2^32), тогда как сама библиотека работает **шестидесятичетырёхбитными**
лимбами. Это другой способ счёта, поэтому ошибка в переносе между половинами
64-битного лимба не может совпасть в обеих реализациях. Эталон не вызывает ни
одной функции `InfiniteCoord`, кроме чтения уже готовой раскладки.

- `TestReferenceAddInt64` — 1500 итераций: случайное значение шириной до
  четырёх лимбов (сборка сдвигами), случайные добавки и крайние
  `INT64_MIN/MAX/±1/0`; проверяются и накопление на месте, и копия.
- `TestReferenceAddInt64Boundaries` — точные края: `(2^64−1)+1`, заём из
  старшего лимба, погашение, смена знака, `2^63 + INT64_MIN`, ноль минус
  `2^63`, `(2^128−1)+1`.

Проверок стало **262 → 7799**, ни одна прежняя не изменена и не удалена.

### 4.2 Фальсификация каждой правки

Каждая правка ломалась намеренно и тест её ловил:

| подмена | что поймало |
| --- | --- |
| убран контроль переноса из одного лимба | «перенос через границу лимба построил не 2^64» |
| при точном погашении значение не обнуляется | «сложение противоположных не дало чистый ноль» |
| у однолимбового перевода в double потерян знак | «точное значение до 2^53» |

### 4.3 Хеши физики

Собраны `laiue_physics_determinism_test`, `laiue_rigid_solver_test`,
`laiue_rigid_cache_test`, `laiue_rigid_broadphase_test`; прогон с DLL до и
после правки даёт одно и то же, и это ожидаемые значения из отчёта по
контактам:

| --- | --- |
| `physics-rebased-hash` | `0x4486debc2d00fab7` |

| `rigid-cached-replay-hash` | `0x58c622ddfd840a45` |

Полный CTest в `build/numeric-peer`: **29/29**, включая

### 4.4 Сборка и предупреждения

`infinite_coord.c` отдельно прогнан `clang -x c` со
`-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Wshadow
-Wunused-function -Werror`:

- x86_64 — чисто;
- `--target=aarch64-pc-windows-msvc` — чисто;
- `-mno-avx -mno-avx2` (scalar-путь без обязательного AVX2) — чисто.

Основная сборка CMake — MSVC Release x64, `/arch:AVX2 /W4 /WX /GL`, без
замечаний.

## 5. Что осталось непроверенным

- Широкий путь подрос на одну проверку; это осознанный размен, а не
  незамеченная регрессия.
- Микробенчмарк измеряет 1–3 нс на операцию и потому чувствителен к
  раскладке кода в DLL: у второго варианта сборки `to_double` уезжал на
  четверть наносекунды вверх и обратно, хотя машинный код функции был
  побайтово одинаков (проверено дизассемблированием), а перевод в double
  упирается только в него самого. Поэтому выводы о выигрыше сделаны по
  операциям, где эффект кратно больше шума, и подтверждены отдельными
  замерами.
- Зонд счётчиков выделений — внешний, в дерево не положен: перехватывать
  аллокатор библиотеки из бенчмарка, линкующегося с DLL, нельзя, а сама
  DLL-сборка CMake занята другим агентом. В отчёте приведены метод и
  детерминированные числа.
- ARM64 и clang проверены компиляцией, а не запуском; запуск был только
  MSVC Release x64. Debug и Linux/macOS не гонялись.

## 6. Как повторить

```powershell
cmake --build build/numeric-peer --target laiue_numeric laiue_infinite_coord_test laiue_numeric_physics_benchmark
build/numeric-peer/bin/Release/laiue_infinite_coord_test.exe
build/numeric-peer/bin/Release/laiue_numeric_physics_benchmark.exe
ctest --test-dir build/numeric-peer -C Release --output-on-failure
```

A/B — подмена только `laiue_numeric.dll` при том же бенчмарке и чередование
заходов: у этих чисел наносекундный масштаб, и последовательные серии
смещаются сильнее, чем сам эффект. Сравнивать надо минимум нескольких серий,
а не один заход.
