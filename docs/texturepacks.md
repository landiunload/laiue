# Текстурпаки

Текстурпак — папка `textures/<name>.ltp`, а не один файл. Внутри лежат
текстуры, названные так же, как материалы приложения, и разложенные по
подпапкам как обычное дерево файлов. Активное UTF-8-имя пака хранится в
`textures/active.txt`; это только имя папки — запрещены separators,
управляющие символы, Windows device names и конечные пробел/точка.

```text
textures/
  active.txt          -> Default
  Default.ltp/
    blocks/
      main/
        stone.png
        stone.normal.png
        water.gif       <- анимированный материал
        sand.jpg        <- фотография читается как есть
      special/
        glow.lt         <- подготовленная текстура
```

**Заменить любую текстуру — значит положить в пак файл с тем же именем.**
Пересобирать пак целиком не нужно, инструмент запускать тоже.

## Имена материалов

Имена задаёт приложение, а не движок: он не знает, что такое «камень».
Список передаётся один раз и применяется при следующей загрузке пака:

```c
static const wchar_t *const materialNames[] = {
    L"blocks/main/stone",
    L"blocks/main/water",
    L"blocks/special/glow",
};
RendererSetMaterialNames(renderer, materialNames, 3u);
```

`BlockType` 1 берёт первое имя, 2 — второе и так далее, до 64 материалов.
Материал 0 зарезервирован для воздуха и обычно не попадает в меш; id
сверх списка зажимается к последнему материалу.

Имя вправе содержать `/` — это путь внутри пака, до восьми сегментов.
Каждый сегмент проверяется как отдельное имя, поэтому ни `..`, ни
абсолютный путь, ни разделитель Windows за пределы пака не выведут.
Расширение в имени не указывается: движок сам ищет файл.

## Что кладётся в папку

| Расширение | Что это |
|---|---|
| `.lt` | подготовленная текстура движка: кадры уже разобраны |
| `.png` | любой тип цвета, глубина 1–16 бит, палитра, `tRNS`, Adam7 |
| `.gif` | палитра, прозрачность, чересстрочность и анимация |
| `.jpg`, `.jpeg` | последовательный и прогрессивный режим, любое прореживание цветности |

## Кэш рядом с исходником

Движок читает чужой формат ровно один раз. Разобрав `stone.png`, он
кладёт рядом `stone.png.lt` и дальше берёт уже его: на следующем запуске
декодирования не происходит вовсе.

```text
      main/
        stone.png       <- исходник, его правит человек
        stone.png.lt    <- кэш, его пишет движок
```

Порядок поиска такой:

1. `stone.png`, `stone.gif`, `stone.jpg`, `stone.jpeg` — первый
   найденный исходник. Рядом с ним ищется `stone.<ext>.lt`:
   - отпечаток в кэше совпал с исходником — берётся кэш;
   - не совпал или его нет — исходник разбирается заново, кэш
     переписывается;
   - исходника нет, а кэш есть — берётся кэш;
   - кэш не разобрался — он не заслоняет живой исходник, тот просто
     читается заново.
2. `stone.lt` — подготовленная вручную текстура. Она берётся как есть,
   движком никогда не переписывается, и кэш рядом с ней не появляется:
   выводить её не из чего.
3. Ничего нет — нейтральный слой и `RENDERER_CONTENT_INCOMPLETE`.

Свой формат стоит **последним** намеренно: он запасной путь, а не
главный. Пока исходник лежит рядом и читается, показывается он — иначе
`stone.lt`, собранный когда-то, навсегда заслонил бы обновлённый рядом
PNG, и «положи новый файл» как способ поменять текстуру перестало бы
работать. А когда исходник пропал, повредился или оказался движку не по
зубам, перебор доходит до `stone.lt` — и материал остаётся на месте.

Отсюда же главное свойство кэша: **удаление исходника не ломает пак**.
Собранная текстура остаётся, и материал продолжает показываться.

### Свой порядок: `formats.txt`

Порядок задаётся файлом `textures/formats.txt` — рядом с `active.txt`, а
не внутри пака: это выбор поставки, а не свойство содержимого. Одно
расширение на строку, точка необязательна, регистр не важен, пустые
строки и строки с `#` пропускаются.

```text
      textures/
        active.txt      -> Default
        formats.txt
```

```text
# готовая игра: ничего не декодировать и ничего не писать
lt
png
```

Файл задаёт **приоритет, а не белый список**: формат, которого в нём
нет, остаётся доступным — просто позже. Иначе одна забытая строка молча
прятала бы содержимое пака. Незнакомое расширение пропускается.

Поставив `lt` первой строкой, приложение получает прежнее поведение:
берётся готовый `stone.lt`, исходник не читается, рядом ничего не
создаётся. Это разумный выбор для установленной игры, где каталог
доступен только на чтение, и наоборот — для разработки удобен порядок по
умолчанию, когда правка PNG видна на следующем запуске.

Свежесть определяет **отпечаток исходника, записанный в сам кэш**: его
размер и время изменения. Проверка стоит одного обращения к каталогу —
исходник при этом не читается, в чём и весь смысл кэша.

Сравнение «кэш новее исходника» обошлось бы без двенадцати байт в
заголовке, но не заметило бы отката файла из старой копии: файл старый,
кэш новый, кэш и остался бы. Отпечаток замечает любую смену личности
исходника и не зависит от того, сравнимы ли часы двух файлов между собой
— перенос пака на другую машину или распаковка архива больше не вызывают
ложных пересборок.

Точным он всё же не является: исходник, изменённый в пределах разрешения
часов и сохранивший размер, будет принят за прежний. Точный ответ дал бы
только хеш содержимого, а для него исходник пришлось бы читать целиком —
то есть делать ровно ту работу, ради устранения которой кэш и заведён.
Никакой базы рядом с паком при этом не появляется: кэш описывает сам
себя.

Запись кэша необязательна: каталог пака бывает доступен только на
чтение — установленная игра, app bundle, консоль. Тогда движок молча
разбирает исходник каждый запуск, и это не ошибка загрузки. Если
декодировать при каждом запуске нежелательно, поставку стоит собрать в
`.lt` заранее и поставить `lt` первым в `formats.txt`.

`.lt` не сжат: он хранит готовые пиксели, и рядом с PNG выглядит
крупнее. Так и задумано — кэш существует ради скорости загрузки, а не
ради места на диске. Класть в пак только `.lt`, собранные заранее,
никто не мешает.

Декодеры собственные, сторонних библиотек у движка нет.

У JPEG нет альфы: слой получается непрозрачным целиком. Прозрачную
текстуру кладите как PNG или GIF. Цветность, записанную вдвое реже
(4:2:0 и 4:2:2), движок восстанавливает треугольным фильтром, как это
делают обычные декодеры; более редкие отношения вроде 4:1:1 повторяют
ближайший отсчёт. Двенадцать бит на отсчёт, арифметическое кодирование
и иерархический режим отвергаются с внятным сообщением, а не
разбираются наполовину.

Одна и та же реализация читает эти форматы и в движке, и в
`laiue_texc`: расхождения между «как оно загрузилось» и «как оно
подготовилось» просто нет.

Карта нормалей и AO — отдельный файл с суффиксом `.normal` в имени:
`stone.png` и `stone.normal.png`. Она обязана совпадать с albedo по
размеру и содержать либо один кадр, либо столько же, сколько albedo.
Готовый `.lt` вправе нести обе карты внутри себя. Там, где карты нет,
renderer подставляет плоскую нормаль с полной открытостью: освещение
вырождается в чистый ламберт по граням.

Материал, файла которого в паке не нашлось или чей файл не разобрался,
показывается нейтральным серым слоем, а загрузка возвращает
`RENDERER_CONTENT_INCOMPLETE`. Это состояние приложения, а не отказ:
опечатка в одном имени не должна лишать пак остальных текстур.

## Размеры

Массив на GPU требует одного размера для всех слоёв. Движок берёт
наибольшую сторону среди загруженных текстур, округляет вверх до степени
двойки (не больше 4096) и приводит к ней остальные усреднением по
площади. Тем же усреднением строится полная mip-цепочка.

Усреднение взвешено по альфе: прозрачные пиксели, у которых цвет обычно
чёрный, не затемняют края при уменьшении. Увеличение повторяет ближайший
пиксель — для пиксель-арта это нужнее сглаживания.

## Анимация

Анимированный GIF даёт материалу столько кадров, сколько в нём есть, и
свою длительность кадра. Кадры занимают по слою массива подряд; всего
слоёв в паке до 256.

Кадр выбирает процессор один раз на проход и кладёт в константы кадра
готовый номер слоя для каждого материала — по байту на материал. На GPU
это значило бы считать одно и то же время в каждой вершине каждого чанка.

Расписание лежит в паке, потому что пришло вместе с картинкой; часы
принадлежат приложению:

```c
RendererFrameSetup frame = { /* ... */ };
frame.animationSeconds = ApplicationClockSeconds();
RendererBeginFrame(renderer, &frame);
```

Пауза — это одно и то же значение два кадра подряд; перемотка — любое
другое. Отрицательное время считается нулём. Материал без анимации от
часов не зависит вовсе.

Задержки у разных кадров вправе различаться — в GIF так можно, и
контейнер это сохраняет: у каждого слоя своя длительность, а цикл длится
столько, сколько они дают в сумме. Кадр с нулевой задержкой означает «как
можно быстрее»; движок берёт то же, что и просмотрщики, — иначе цикл
получился бы нулевой длины.

## Формат LT

Одна текстура своего формата. Все числа little-endian, header 24 байта:

| Offset | Тип | Значение |
|---:|---|---|
| 0 | `u32` | magic `LTS1` (`0x3153544C`) |
| 4 | `u16` | version = 2 |
| 6 | `u16` | header size = 40 |
| 8, 10 | `u16` | width, height: 1–4096 |
| 12 | `u16` | кадров: 1–256 |
| 14 | `u16` | миллисекунд у первого кадра; 0 допустим только при одном кадре |
| 16 | `u16` | format: 1 — только albedo, 2 — albedo и normal/AO |
| 18 | `u16` | зарезервировано, 0 |
| 20 | `u32` | размер payload |
| 24 | `u64` | время изменения исходника |
| 32 | `u32` | размер исходника; 0 — файл ни из чего не выведен |
| 36 | `u32` | зарезервировано, 0 |

Отпечаток заполняет движок, когда собирает кэш из PNG, GIF или JPEG. У
файла, собранного `laiue_texc` или положенного руками, он нулевой: такой
файл — авторское содержимое, а не кэш, и устареть не может.

За заголовком идёт расписание: по `u16` на кадр, миллисекунды. При
нескольких кадрах ни одно значение не может быть нулевым — кадр без
длительности остановил бы анимацию молча. Поле по смещению 14 дублирует
первое значение, чтобы расписание было видно, не читая таблицу.

Payload — кадры подряд, каждый RGBA8 `width × height` со строками
вплотную; при format 2 следом идёт такой же блок карт нормалей. Размер в
заголовке считает только пиксели, расписание в него не входит. Mip-
уровней в файле нет: общий размер массива известен только после чтения
всего пака, и цепочка всё равно строится при загрузке.

Расхождение размера с заголовком отвергается как повреждение.

Версия 1 хранила одну длительность на всю анимацию, не знала об
отпечатке и занимала 24 байта. Она читается по-прежнему: файл, собранный
прежней сборкой, не обязан устаревать вместе с форматом. Пишется всегда
версия 2, а кэш без отпечатка считается устаревшим и пересобирается при
первой же загрузке.

## Подготовка `.lt`

`.lt` собирает офлайн-конвертер `laiue_texc` из `tools/texc`. Он входит
в сборку при `LAIUE_BUILD_TOOLS=ON` — по умолчанию везде, кроме
кросс-сборки и внешнего платформенного профиля, — и в SDK не
устанавливается.

```sh
laiue_texc stone.png blocks/main/stone.lt
laiue_texc --size 64 --normal water_n.png water.gif blocks/main/water.lt
laiue_texc photo.jpg blocks/main/photo.lt
```

| Опция | Смысл |
|---|---|
| `--size N` | привести к N×N перед записью |
| `--normal <file>` | добавить карту нормалей и AO в тот же файл |
| `--help` | краткая справка |

Инструмент необязателен: PNG, GIF и JPEG в паке работают как есть. `.lt` нужен
там, где загрузку хочется ускорить — он уже разобран, и на старте
остаётся только скопировать пиксели. Запись атомарна. Коды возврата: `0`
— успех, `1` — файл не прочитан, не разобран или не записан, `2` —
ошибка в аргументах.

## Границы

Текстурпак меняет только отображение материала. Коллизии и остальные
прикладные свойства задаются отдельно от renderer. Имена и физические
свойства материалов в паке не хранятся: он отдаёт текстуру по имени, а
что это за материал — знает приложение.

При первой подготовке без активного валидного пака используется
нейтральный встроенный 1×1 fallback. При hot reload повреждённый пак,
I/O error или ошибка создания GPU resource оставляют прежние texture
arrays и descriptors активными. `RendererReloadTexturePackFrom` читает
явный каталог и выполняет замену только после полного создания albedo и
normal/AO replacement.
