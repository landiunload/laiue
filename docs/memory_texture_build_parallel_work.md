# Двухпроходная сборка текстурного пака: пик памяти и побайтовое равенство

Отчёт по задаче «срезать транзиентный пик памяти при сборке текстурного
пака». Изменён один файл движка — `src/render/texture_build.c`
(`TexturePackBuildFrom`, `LoadResource`, `LoadMaterial` и их помощники):
+253/−40 строк. Публичный API и ABI не менялись, новых экспортов нет,
`dumpbin /exports laiue_render.dll` даёт тот же список из пяти функций
`TexturePack*`. На момент исходного замера CMake не менялся; позже для
регрессии добавлена отдельная тестовая цель. `src/media/image.c` не тронут:
`ImageInspect`/`ImageDecode`/`ImageResample` вызываются как есть.

Стенд лежит в `build/peer/` (каталог `build/` в `.git` игнорируется, это
не часть дерева исходников): `texpeak_profile.c`, `gen_pack.py`,
`texpeak_stand.bat`.

## 1. Схема двух проходов

Было (один проход «всё в ОЗУ, потом сборка»):

1. цикл `LoadMaterial` по всем материалам — каждый раскодируется целиком
   (`ParseSingleTexture` для `.lt`/кэша, `ImageDecode` для PNG/JPEG/GIF) и
   живёт в `sources[]` до конца;
2. только теперь известен `largest` → `size` → выделяется пак `pixels`;
3. цикл записи: каждый источник ресемплится в цепочку мипов и **лишь
   тогда** освобождается.

Стало:

1. **Проход 1 — только заголовки.** `LoadMaterialMeta` → `LoadResourceMeta`
   для каждого материала:
   - свой `.lt` и кэш: новый `ParseSingleTextureHeader` проверяет заголовок
     (версия, формат, размеры, расписание, отпечаток исходника) и **не
     копирует пиксели**;
   - PNG/JPEG/GIF: `ImageInspect` (новый `InspectImageMeta`) даёт размеры и
     число кадров без декодирования;
   - карта нормалей: разрешается тем же перебором форматов, а совпадение
     геометрии проверяется по заголовкам (`normal.width/height/frameCount`
     против albedo) — ровно как в старом `LoadMaterial`. Существования
     файла недостаточно, иначе `.normal`, не подходящий по размеру, менял
     бы геометрию пака и байты.
   Итог: `largest`, `sliceCount`, `anyNormal`, `missing` — те же значения,
   что давал прежний первый цикл. Кэш при этом **не пишется**.
2. Сразу после прохода 1 известны `size` и `sliceCount` — пак `pixels`
   выделяется один раз.
3. **Проход 2 — по одному материалу:** `LoadMaterial` → `WriteSliceChain`
   в пак → `ReleaseSource` → следующий. Порядок слоёв, `animation[]`,
   `sliceMilliseconds[]`, `WriteConstantChain` для `missing` и запись кэша
   `WriteTextureCache` при первом декодировании сохранены дословно.

`LoadResource` не переписывался: полный разбор теперь строится поверх
`ParseSingleTextureHeader`, поэтому заголовочная проверка в обоих проходах
одна и та же.

В исходной редакции отчёта проход 1 читал файл **целиком** через
`PlatformReadEntireFile`; приведённые ниже временные замеры относятся к
этому варианту. В текущей редакции движка `.lt` и `.lt`-кэш используют
`PlatformReadFilePrefix`: заголовок и таблица длительностей читаются в
фиксированный scratch, а полный размер проверяется тем же handle. PNG,
JPEG и GIF по-прежнему инспектируются после полного чтения — для них
потоковый cursor-контракт ещё не введён.

## 2. Пик памяти до/после

Пак: 64 материала 256×256, альбедо + нормали, без анимации
(`sliceCount = 64`, мипов 9, цепочка на слой 349 524 Б). Перехват
`HeapAlloc`/`HeapFree`/`HeapReAlloc` по IAT главного модуля и
`laiue_content.dll`; таблица указатель→размер, живой объём и пик. Пик —
это максимум живого объёма за вычетом объёма до вызова.

| режим | до, Б | до, МиБ | после, Б | после, МиБ |
| --- | ---: | ---: | ---: | ---: |
| тёплый `.lt`-кэш | 78 329 344 | **74.700** | 45 723 434 | **43.610** |
| холодный PNG | 78 329 344 | **74.700** | 45 725 482 | **43.612** |

Собранный пак — 44 739 072 Б (42.666 МиБ). То есть:

* до: пак (42.67 МиБ) + **все** раскодированные источники (32.00 МиБ) +
  массив `sources[]` (35 328 Б) = 74.70 МиБ;
* после: пак (42.67 МиБ) + **один** материал (0.50 МиБ) + скретч загрузчика
  (0.19 МиБ) + транзиентный буфер одного файла (0.25 МиБ) + таблица
  `metas` (1 КиБ) = 43.61 МиБ.

Снижение пика: **32 605 910 Б = 31.10 МиБ на пак, то есть на 41.6 %**.
Для холодного PNG цифры совпадают: пик задаёт пак, декодер в него не
упирается (см. раздел 5).

## 3. Время до/после

Минимум из 5 чередующихся прогонов «до/после» внутри одного окна (стенд
запускает варианты вперемешку, чтобы дрейф общей машины не приписывался
одному из них); приведён лучший из нескольких запусков стенда. Флаги
`/O2 /Ob3 /GL /LTCG`, как у Release-сборки движка.

| режим | до, мс | после, мс | отношение |
| --- | ---: | ---: | ---: |
| тёплый `.lt`-кэш | 157.75 | 186.19 | 1.18× |
| холодный PNG | 538.16 | 609.04 | 1.13× |

**Почему тёплый режим в исходном замере был дороже.** До появления
`PlatformReadFilePrefix` проход 1 читал `.lt`-кэш целиком: 64 материала ×
(альбедо + нормаль) ≈ 32.0 МиБ дополнительного чтения (проход 2 читает их
ещё раз). Сейчас этот повторный payload-read устранён для `.lt`; указанное
в таблице +18 % — историческая верхняя граница старого пути, а не обещание
для текущей реализации.

**Почему холодный режим дороже.** К декодированию добавляется второй
`ImageInspect` на каждый файл (проход 1) и повторные обращения к каталогу;
на фоне распаковки 32 МиБ пикселей это +13 %. Абсолютный выигрыш памяти —
31 МиБ — на слабой машине важнее 70 мс разовой загрузки.

## 4. Побайтовое равенство

Стенд собирает **один и тот же** пак прежней редакцией
(`build/peer/texture_build_before.c`, снята через
`git show HEAD:src/render/texture_build.c`) и текущей и сравнивает не
только `size`/`sliceCount`/статус, но и все пиксели, `animation[]` и
`sliceMilliseconds[]`.

### Фикстуры `tests/texc_fixtures.h`

Один пак из девяти материалов: три PNG (RGBA, палитра, gray16,
interlaced), два GIF (в том числе с неровным расписанием 40/120/60 мс),
JPEG, свой `.lt` с **встроенной** картой нормалей и отсутствующий
материал. У `rgba` карта нормалей совпадает по геометрии (4×4), у `jpeg` —
нет (8×8 при albedo 16×16) и обязана быть отброшена.

Результат прогона (обе реализации, холодные кэши):

```
fixtures: before(status=5 size=16 slices=13 albedo=d52c7c3e0eccfedc normal=07be8e1cad94384b)
fixtures: after (status=5 size=16 slices=13 albedo=d52c7c3e0eccfedc normal=07be8e1cad94384b)
fixtures: cache written for png source = yes, mismatches = 0
```

`status=5` — `TEXTURE_PACK_LOAD_INCOMPLETE` (одного материала нет),
`size=16`, `sliceCount=13`; хэш Fnv-1a 64 совпадает и для альбедо, и для
нормалей. Сторонний эффект `LoadResource` сохранён: после сборки рядом с
`rgba.png` лежит `.png.lt`.

### Большой пак

64 материала 256×256 с нормалями, холодные PNG:

```
bench pack: status=1 size=256 slices=64 albedo=c837f4ca25c1a943 normal=4c1d80591d5d9b03 equal=yes
```

`status=1` — `TEXTURE_PACK_LOAD_OK`.

### Фальсификация

Чтобы проверка не проходила вхолостую, в текущей реализации намеренно
сломано одно место — `InspectImageMeta` возвращал `frameCount = 1`.
Стенд поймал: `fixtures ... slices=9` против `13`,
`mismatches = 18`, код возврата 1 (в том числе `albedo bytes`,
`normal bytes`, `animation.frameCount`, `sliceMilliseconds`). Правка
откачена из резервной копии — снова `mismatches = 0`.

## 5. Что осталось в пике после

От пакета (44.739 МБ) пик 45.723 МБ превышают:

| остаток | байт | природа |
| --- | ---: | --- |
| один раскодированный материал (albedo+normal) | 524 288 | неизбежно: именно его и ресемплим |
| `LoadScratch` (3 пути по 32 КиБ + имя) | 196 864 | удерживается через оба прохода |
| транзиентный буфер одного `.lt`/файла | 262 184 | `PlatformReadEntireFile`, освобождается сразу |
| таблица `metas` на 64 материала | 1 024 | вместо `sources[]` всех материалов |

Скретч декодера PNG на файлах 256×256 мал: холодный пик превысил
тёплый всего на 2 КиБ (2 048 Б), то есть декодер не добавляет заметного
сверх «пак + один материал + буфер файла».

## 6. Сборка и тесты

* `cmake --build --preset windows-msvc-release --parallel 3` — без
  предупреждений (они ошибки), проверка границ архитектуры
  `OK (105 files)`.
* `ctest --preset windows-msvc-release --no-tests=error` — **30/30**.
* Сам стенд: `fixtures` — `mismatches = 0`, `equal=yes`; `bench` — без
  неожиданных статусов.

## 7. Где живёт проверка и почему не в `tests/`

`TexturePackBuildFrom` **не экспортируется** из `laiue_render.dll`
(проверено `dumpbin /exports`: наружу идут только `TexturePackActivate`,
`TexturePackActivateIn`, `TexturePackEnumerate`, `TexturePackEnumerateFrom`,
`TexturePackListRelease`). Поэтому из `tests/render_pack_api_test.c` его не
вызвать без новых экспортов, а новые экспорты запрещены; `tests/texc_test.c`
и вовсе линкуется только с `laiue_media_support`. Сквозной публичный путь
сборки пака — `RendererReloadTexturePackFrom`, но он требует рендерера, а
`laiue.render.offscreen_frame` в этом профиле (D3D12) не собирается.
Поэтому равенство «до/после» сначала закреплялось отдельным стендом
(`build/peer/texpeak_profile.c`), компилирующим и прежнюю, и текущую
редакции `texture_build.c` в один процесс. Теперь тот же путь дополнен
детерминированным `laiue.render.texture_build`: он компилирует внутренний
сборщик в отдельную тестовую цель и сверяет холодную/тёплую сборку, кэш,
расписание кадров и карты нормалей. Публичный
`laiue.render.offscreen_frame` (когда собирается под Vulkan) по-прежнему
проверяет собранный пак по цвету пикселей.

## 8. Ограничения и отклонённое

* **Растерные заголовки.** Для `.lt` и `.lt`-кэша первый проход теперь
  использует `PlatformReadFilePrefix`: заголовок и таблица длительностей
  читаются без выделения памяти размером с payload, а полный размер
  проверяется на том же handle. PNG/JPEG/GIF пока проходят через
  `PlatformReadEntireFile`, потому что их инспекторы не имеют потокового
  cursor-контракта; переносить их на произвольный prefix без изменения
  семантики декодеров нельзя.
* **Переиспользование `ImageInfo` между проходами** (убрало бы второй
  `ImageInspect`) отклонено: усложняет путь кэша/исходника и не влияет на
  пик, ради которого задача. Скретч декодера и так не доминирует.
* **`src/media/image.c` не тронут** — параллельная правка `ImageResample`
  идёт отдельно; `texture_build.c` вызывает её как есть.
* **Vulkan-бэкенд не измерялся** (здесь D3D12); двухпроходная сборка
  бэкенд-нейтральна, её зовёт общий `TexturePackLoadActiveFrom`.

## 9. Воспроизведение

```bat
build\peer\setup.bat
build\peer\texpeak_stand.bat
```

`texpeak_stand.bat` компилирует `src/render/texture_build.c` (текущая) и
`build/peer/texture_build_before.c` (прежняя, `git show HEAD`) в один
`build/peer/texpeak_profile.exe`, генерирует `gen_pack.py` 64 материала
256×256 с нормалями и запускает `fixtures` и `bench`. Полная сборка и
тесты:

```bat
cmake --build --preset windows-msvc-release --parallel 3
ctest --preset windows-msvc-release --no-tests=error
```
