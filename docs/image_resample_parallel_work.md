# Ресемплер изображений: копия 1:1 и точное уменьшение вдвое

Затронуты [src/media/image.c](../src/media/image.c) (только `ImageResample`) и
тесты: новый [tests/image_resample_test.c](../tests/image_resample_test.c) с
регистрацией в [tests/CMakeLists.txt](../tests/CMakeLists.txt). Публичный
`media/image.h`, сигнатура и ABI не менялись, новых экспортов нет: таблица —
`static const`, вспомогательных внешних функций не добавлено. Чужой
`src/render/texture_build.c` и декодеры (`png_decode.c`, `jpeg_decode.c`,
`inflate.c`) не трогались.

Результат побайтово прежний для **любых** входов. Быстрые пути включаются
только при точных условиях и покрывают ровно те вызовы, что делает сборка
текстурного пака: сначала `источник → size×size` (обычно 1:1), затем цепочку
мипов `size → size/2 → … → 1`. Всё остальное (увеличение и произвольное
уменьшение) идёт прежним общим кодом, который остался в функции как эталон.

## 1. Что изменено

### 1.1 Быстрый путь 1:1

Если `sourceWidth == destinationWidth` и `sourceHeight == destinationHeight`,
результат общего пути совпадает с исходником, и вместо циклов выполняется
`memcpy` (с проверкой `source != destination`). Это самый тяжёлый по объёму
случай: в паке так приводится к общему размеру каждая текстура — 128 копий
256² на пак (см. §5).

### 1.2 Быстрый путь уменьшения вдвое

Если `sourceWidth == 2·destinationWidth` и `sourceHeight == 2·destinationHeight`,
каждый выходной пиксель — ровно блок 2×2. Границы не считаются, суммы лежат в
32 битах (`alphaSum ≤ 1020`, `weighted ≤ 255·1020`). Деление с округлением
`(w + a/2)/a` заменено умножением на таблицу `kAlphaReciprocal` и одним
условным декрементом. Таблица — `static const uint32_t[1021]` в `.rdata`, не на
стеке; кадр функции остаётся в пределах 4 КиБ.

## 2. Доказательство эквивалентности

### 2.1 Копия 1:1

При совпадающих размерах `firstRow = row`, `lastRow = row + 1`, то же по
столбцам. Значит блок — один пиксель: `samples = 1`, `alphaSum = alpha`,
`weighted = texel·alpha`, `plain = texel`.

- `alpha ≠ 0`: `(texel·alpha + alpha/2)/alpha = texel + (alpha/2)/alpha`, а
  `0 ≤ (alpha/2)/alpha < 1`, поэтому целочисленное частное равно `texel`.
- `alpha = 0`: `(texel + 1/2)/1 = texel`.
- альфа: `(alpha + 1/2)/1 = alpha`.

Итог — `out[c] = texel[c]` для всех каналов, то есть побайтовое копирование.

### 2.2 Уменьшение вдвое

`firstRow = 2·row`, `lastRow = 2·row + 2` (то же по столбцам): блок 2×2,
`samples = 4`. Тогда

- непрозрачный блок: `out[c] = (w + a/2)/a`, где `w = Σ texel[c]·alpha`,
  `a = alphaSum`;
- прозрачный блок: `out[c] = (Σ texel[c] + 2)/4`, потому что `samples/2 = 2`;
- альфа: `out[3] = (a + 2)/4`.

Все слагаемые целые: `a ≤ 4·255 = 1020`, `w ≤ 255·a ≤ 260 100`,
`Σ texel[c] ≤ 1020` — 32 бита с запасом.

**Перевод округления в умножение.** Тождество

```
(w + a/2)/a = floor((2w + a) / (2a))
```

верно, потому что `a/2 = floor(a/2)`, а дробная добавка `(a mod 2)/2` не
переводит частное через целую границу. Пусть `M[a] = ceil(2^24 / (2a))` — это
`kAlphaReciprocal[a]`, `e = M[a]·2a − 2^24 ∈ [0, 2a)`. Тогда для `m = 2w + a`

```
m·M/2^24 = m/(2a) + m·e/((2a)·2^24),
```

и добавка строго меньше `m/2^24`, потому что `e < 2a`. При `w ≤ 255a` имеем
`m ≤ 511a ≤ 511·1020 = 521 220`, значит добавка `< 521 220/2^24 = 0,031 < 1`.
Следовательно `q0 = (m·M) >> 24` больше `floor(m/(2a))` не более чем на
единицу, и одного декремента при `q0·2a > m` достаточно.

**Почему произведение влезает в 32 бита.** `M[a] ≤ 2^23/a + 1`, поэтому
`m·M ≤ 511a·(2^23/a + 1) = 511·2^23 + 511a ≤ 4 286 103 552 + 521 220 =
4 286 624 772 < 2^32`. Переполнения нет ни при одном допустимом входе.

### 2.3 Прозрачный блок

При `a = 0` общего пути соответствует ветка обычного среднего
`(Σ texel[c] + samples/2)/samples`; при `samples = 4` это `(Σ + 2)/4`, то есть
сдвиг с константой. Альфа при этом `(0 + 2)/4 = 0`.

## 3. Проверка

### 3.1 Тест дерева

[tests/image_resample_test.c](../tests/image_resample_test.c) содержит
**дословную копию прежней общей реализации** `ReferenceResample` и сравнивает с
ней `ImageResample` побайтово:

- все размеры источника 2…64, копия 1:1 — 3 969 сверок;
- те же чётные размеры (32 значения на сторону), уменьшение вдвое — 1 024
  сверки; в верхний блок 2×2 каждого случая принудительно ставится полностью
  прозрачный блок с ненулевым цветом;
- 10 000 случайных пар размеров 2…64 в обе стороны (включая увеличение);
- отдельно: целиком прозрачный блок 2×2 (цвет берётся обычным средним —
  проверено значение `88/26/33`) и блок из максимумов `255/255/255/255`.

Итого **14 993** независимых сравнения в счётном цикле (плюс две явные крайние
сверки), каждое — по всем байтам выхода. Все они проходят на новой реализации.

### 3.2 Контрольная сумма mip-цепочки

Генератор — тот же xorshift с зерном `0x12345678`, что в стенде. Цепочка
256 → 128 → … → 1 прогоняется и новой, и эталонной реализацией **с побайтовой
сверкой каждого уровня**, затем обе суммы сверяются с константой

```
CHAIN_CHECKSUM = 0x9ad25e9b6cea9c76
```

снятой стендом с **неизменённого** старого кода. Совпадение всех трёх величин
зафиксировано.

### 3.3 Исчерпывающая проверка таблицы

Стенд `build/peer/image_resample_bench.c` подключает текст `src/media/image.c`
с вырезанным `static` и потому читает **ровно ту таблицу**, что лежит в
рабочем коде. Для всех `alphaSum ∈ [1, 1020]` и всех достижимых числителей
`0 … 255·alphaSum` (сумма — 132 782 070 значений) `q = (m·M) >> 24` с
поправкой сравнивается с эталонным делением `(w + a/2)/a`. Итог: `PASS`,
расхождений нет.

## 4. A/B-замеры

Стенд `build/peer/image_resample_bench.c` держит копию старой функции
(`OldImageResample`) и вызывает новую из того же текста; заходы чередуются,
минимум из 7 серий по 128 повторов. MSVC Release x64, `/O2 /Ob3 /GL`.

| нагрузка (128 повторов) | до, мкс | после, мкс | ускорение |
| --- | ---: | ---: | ---: |
| `256 → 256` (копия) | 77 862,9 | 458,6 | **×169,8** |
| `256 → 128` (вдвое) | 30 264,0 | 11 055,2 | **×2,74** |
| цепочка `256 → 1` | 118 615,6 | 14 956,9 | **×7,93** |

В пересчёте на один вызов: копия `608,3 → 3,6 мкс`, уменьшение
`236,4 → 86,4 мкс`, цепочка `926,7 → 116,9 мкс`. Второй прогон дал те же
числа в пределах ~2 % (×169,8/×2,74/×7,93 против ×171,1/×2,79/×7,75).

## 5. Что это даёт на паке 64 материала 256²

Паку соответствует 64 материала × 2 слоя (albedo и нормали) = **128 цепочек**.
В каждой цепочке 1 вызов `источник → 256` и 8 шагов мипов (256→128, …, 2→1) —
**9 вызовов**, суммарно 87 381 выходной пиксель на цепочку, или
**11 184 768 пикселей и 1 152 вызова** на пак.

По замеру цепочки:

| | было | стало | Δ |
| --- | ---: | ---: | ---: |
| пак 128 цепочек | 118,6 мс | 15,0 мс | **−103,6 мс, ×7,9** |
| в т. ч. копии 1:1 (128 вызовов) | 77,9 мс | 0,46 мс | −77,4 мс |
| в т. ч. мипы 2× (1024 вызова) | 40,7 мс | 14,5 мс | −26,2 мс |

То есть сотни миллисекунд на загрузку пака превращаются в полтора десятка:
основной выигрыш даёт копия 1:1, а шаги мипов ускоряются ещё почти втрое.

## 6. Сборка, предупреждения, ограничения

- MSVC Release x64, `/arch:AVX2 /W4 /WX /GL /Ob3` — без замечаний.
- Новых файлов вне `tests/` и `src/media/image.c` нет; `image.h` не изменён,
  ABI модулей не затронут (таблица `static`, новых экспортов нет).
- Только C17 и обычные циклы: интринсиков и SIMD нет, ARM64/musl/macOS
  собираются тем же кодом. `memcpy` уже используется в дереве, включая
  no-CRT-сборку Windows (`src/runtime/memory.c`).
- Полный CTest в `build/windows-msvc`, конфигурация Release: **31/31**, в том
  числе новый `laiue.media.resample`.
- Не проверено запуском: Linux/macOS/ARM64 (собираемость обеспечена обычным
  кодом, но прогона не было); Debug-профиль.
