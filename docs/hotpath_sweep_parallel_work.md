# Разведка непроверенных файлов: что из них вообще горячий путь

Работа велась в изолированном дереве `laiue-sweep`, ветка `peer/sweep`.
Исходники после разведки не изменены: `git diff` пуст, `src/` и `tests/`
побайтово те же. Всё, что написано для измерения, лежит вне дерева — в
`build/peer/` (в сборку и в архив не входит). Причина, почему правки нет,
разобрана в разделе 5: единственная правка, которую можно было сделать в
единственном горячем файле, в честном A/B выигрыша не показала и откачена.

Главный вывод короткий. Из всего списка «неоткрытых» файлов на кадровом или
шаговом пути движка лежит ровно один — `src/numeric/infinite_coord.c`. И
именно его горячие входы (`InfiniteCoordTryAddInt64InPlace`,
`InfiniteCoordToDoubleSaturating`) уже оптимизированы раньше, а оставшиеся
функции по детерминированным счётчикам вызываются тысячи раз реже. Все
остальные файлы списка вызываются при загрузке/выключении или из
приложения, а не из кадрового цикла движка. Ни в одном не нашлось
избыточной работы, которую стоит убирать.

## 1. Среда и метод

- Windows x64, MSVC 19.44.35228, CMake/Ninja Multi-Config, preset
  `windows-msvc` (Release, AVX2, LTO `/GL`, `/W4 /WX /Ob3`).
- Сборка и тесты — как в задании: `build/peer/setup.bat`, затем
  `cmake --build --preset windows-msvc-release --parallel 4` и
  `ctest --preset windows-msvc-release --no-tests=error`. Базовое состояние
  до и после разведки — **30/30**.
- «Горячий» здесь означает: вызывается на каждом шаге физики, при каждом
  запросе блока мира, в каждом кадре или на каждом буфере звука. Признак
  «вызывается только из `CreateApplication`/`PrepareWorld`» горячим не
  считается.
- Для определения вызовов использован `grep` по `src/`, плюс песочные
  зонды в `build/peer/`:
  - `sweep_probe.c` — наносекунды на вызов отдельных функций `numeric`
    (линкуется с готовой `laiue_numeric.dll`);
  - `panorama_probe.c` — цена `PanoramaBuildFrameSetup` на кадр;
  - `wide_probe.c` — контролируемое сравнение старой и новой реализации
    широкого пути сложения в одном модуле трансляции.
- Оговорка про границу: приложение `simulation-of-sins/src/app/application.c`
  лежит **вне** разрешённого дерева, поэтому напрямую не читалось. Вызовы
  проверялись по `src/render/renderer_d3d12.c` и `src/scene/chunk_streaming.c`,
  а для `panorama.c`/`camera.c` опирался на то, что это экспортируемые
  функции сцены, которые вызывает приложение (в задании сказано, что
  панорама рисуется каждый кадр).

## 2. Вердикт по каждому файлу

| файл | горячий? | доказательство |
| --- | --- | --- |
| `src/numeric/infinite_coord.c` | **да** | единственные потребители — `rigid_body.c` (шаг физики) и `world_infinite.c` (хеш координаты чанка при каждом запросе блока); см. раздел 3 |
| `src/scene/panorama.c` | нет по цене | `PanoramaBuildFrameSetup` в дереве никем не вызывается (только объявление/определение и приложение); измеренная цена — **≈143 нс** на кадр, см. 4.1 |
| `src/scene/camera.c` | нет по цене | вызывается приложением раз в кадр; 4 тригонометрических вызова и ~40 flops; кешировать `sin/cos` нельзя без изменения публичной `struct Camera` (ABI запрещён) |
| `src/content/content_catalog.c` | нет | все вызовы — из загрузчиков паков (`shader_pack.c`, `texture_pack.c`, `audio_pack.c`, `texture_build.c`) и тестов; `renderer_d3d12.c` зовёт каталог только из `RendererPrepareWorldFrom`/`RendererReload*`, не из `RendererBeginFrame`/`EndFrame` |
| `src/mod/mod_host.c` | нет | `LaiueModHost*` вне `mod_host.c` не вызывается ни одной `.c` движка; API — только жизненный цикл (`Create`/`Load`/`Unload`/`RegisterService`), кадрового тика нет |
| `src/mod/mod_manifest.c` | нет | единственный потребитель — `mod_host.c` при загрузке пака (`LaiueModManifestSelectNativeEntry`, `mod_host.c:513`) |
| `src/render/shader_pack.c` | нет | `ShaderPackLoadActiveSet` зовётся только из `RendererReloadShaderPackFrom` (`renderer_d3d12.c:2857`, `renderer_vulkan.c:2512`), то есть при загрузке/перезагрузке |
| `src/render/texture_build.c` | нет | `TexturePackBuildFrom` зовётся только из `TexturePackLoadActiveFrom` (`texture_pack.c:85`); пак строится один раз при подготовке мира |
| `src/audio/audio_pack.c` | нет | нет ни одного вызова из `src/`; разбор/декод звука идёт при создании клипа приложением, не в кадре |
| `src/audio/audio_offscreen.c` | нет | бэкенд-заглушка: `OffscreenDestroy`/`OffscreenUnderrunCount`, никакой работы на кадр; тяжёлое смешивание — в `audio_mixer.c` (зона другого агента) |
| `src/audio/audio_alsa.c` | нет на этой машине | Linux-бэкенд, грузится динамически; поток вывода раз в период зовёт `render` (микшер, `audio_alsa.c:123`), сам бэкенд работы не добавляет. На Windows не исполняется |

Отдельно про «за кадр» в рендерере: единственная безусловная работа на кадр,
задевающая перечисленные файлы, — `TexturePackFillSliceTable`
(`renderer_d3d12.c:2304`), но это `texture_pack.c` (зона другого агента), и
каталог контента там не читается.

## 3. Единственный горячий файл: `infinite_coord.c`

### 3.1 Почему он горячий

`InfiniteCoord` — представление позиций и скоростей физики и координат
чанков мира. `grep` по `src/` даёт ровно трёх потребителей: сам `numeric`,
`src/physics/rigid_body.c` и `src/world/world_infinite.c`.

- **Физика.** `InfiniteCoordTryAddInt64InPlace` вызывается на шаг много раз:
  `rigid_body.c:266` (`TryAddDoubleToFixed`), `:776`
  (`VoxelRigidBodyTranslateBlocks`), `:5101` (`IntegrateBody`); скорость
  читается через `InfiniteCoordToDoubleSaturating` (`rigid_body.c:161`).
- **Мир.** `HashLocalChunkCoordinate` (`world_infinite.c:116`) на каждый
  поиск в таблице делает **три** вызова `InfiniteCoordHashOffset`
  (`world_infinite.c:119`–`:124`); `WorldFindEntry` зовётся при каждом
  запросе блока в мире с правками.

### 3.2 Горячие входы уже оптимизированы

Ранняя правка (коммит `6d32347`) сделала однолимбовые пути
беспереносного сложения и перевода в `double` листьями без обращения к
куче. Детерминированный счётчик из
[`numeric_hotpath_parallel_work.md`](numeric_hotpath_parallel_work.md)
(512 тел, три оси, 64 тика) показывает, что на реальном шаге почти весь
поток — это как раз эти два входа, а «общая» арифметика молчит:

| вход | вызовов за прогон |
| --- | ---: |
| `TryAddInt64InPlace` (тик) | 294 912 |
| `TryCopyAddInt64` | 128 |
| `TrySetFromDouble` | 128 |
| `TryCopyShiftRight` | 128 |
| `TryCopyShiftLeft` | 128 |
| `TryAdd` | 128 |
| `TryCopyNegate` | 128 |
| `TryCopyMultiplyInt64` | 128 |
| `TryCopySquareAddInt64` | 128 |

То есть «сложение/вычитание многоразрядных, сравнение, сдвиги» на шаге
физики — это 128 вызовов против 294 912 у оптимизированного листа, доля
**0,04 %**. Оптимизировать их «отдельно от горячего пути» смысла нет: они и
есть холодный путь.

### 3.3 Микробенчмарк оставшихся функций

Собственный зонд `build/peer/sweep_probe.c` линкуется с готовой
`laiue_numeric.dll` и меряет отдельные функции (минимум из 15 серий):

| функция | нс/вызов |
| --- | ---: |
| `InfiniteCoordHashOffset` (1–2 лимба, случайный знак) | 2,93 |
| `InfiniteCoordToDoubleSaturating` (1 лимб) | 2,19 |
| `InfiniteCoordTryCopyShiftRight` (1 лимб) | 36,3 |
| `InfiniteCoordTryAdd` (пара 1-лимбовых) | 47,0 |

Первые две — горячие и быстрые. Сдвиг вправо и сложение пары упираются в
`PlatformAllocate`/`PlatformFree`: каждая операция рождает собственную
структуру с указателем на лимбы, и это минимум для публичного ABI. На шаге
физики они не встречаются (см. таблицу выше): `IntegrateBody` уходит в
`TryCopyShiftRight` только для ширины больше `int64` (`rigid_body.c:5110`), а
`AngularStepRadians` — только когда угловая скорость не влезает в `int64`
(`rigid_body.c:5047`). Хеш уже разбирал агент `getblock` и нашёл его
допустимым (`hash_x3` = 7,42 нс, попытка сменить функцию хеша подтверждённого
выигрыша не дала).

## 4. Точечные замеры того, что могло быть горячим по незнанию

### 4.1 `panorama.c`

Комментарий в заголовке обещает, что прямоугольники и проекции
пересчитываются только при смене поля зрения/размера, и это подтверждается
кодом: `RebuildCache` вызывается лишь при несовпадении кеша
(`panorama.c:449`–`:465`). На кадр остаётся построение кадрового описания:
на каждый проход `FaceBasisMatrix` плюс два `Matrix4Multiply`
(`panorama.c:483`–`:488`).

Зонд `build/peer/panorama_probe.c` (1920×1080, 15 серий по 20 000 кадров):

| режим | нс/кадр |
| --- | ---: |
| рыбий глаз 170°, кеш прогрет | 143 |
| цилиндр 170°, кеш прогрет | 100 |
| перспектива 90° | 57 |

Против 552–636 мкс `EndFrame` из
[`render_profile_parallel_work.md`](render_profile_parallel_work.md) это
0,02–0,03 % кадра. Свёртка `view * (faceBasis * faceProjection)` убрала бы
один `Matrix4Multiply` на проход, но это перестановка сомножителей
(`(view*faceBasis)*faceProjection` даёт другой float-результат), а правила
дня требуют неизменного результата и запрещают менять порядок операций.
Оптимизировать здесь нечего.

### 4.2 Прочее

`camera.c` — четыре `ScalarSin/ScalarCos` и аффинная сборка `view`; `sin/cos`
не закешировать без правки публичной `struct Camera` (ABI). `audio_alsa.c`
исполняется только на Linux и всё тяжёлое делегирует микшеру. Загрузчики
паков (`content_catalog`, `shader_pack`, `texture_build`, `audio_pack`) и
моды (`mod_host`, `mod_manifest`) в кадровом цикле не встречаются (таблица
раздела 2).

## 5. Отклонённая правка: широкий путь сложения

Единственное место в горячем файле, где вообще была видна «лишняя» работа, —
холодная `InfiniteCoordTryAddInt64InPlaceWide`. Он вызывается ровно из
одного места (`infinite_coord.c:300`) и только когда знак добавки
противоположен знаку величины в два и более лимбов. Значит, проверки
`sign == addSign`, сравнение модулей и ветка «добавка больше» внутри него
недостижимы, а для двух и более лимбов модуль заведомо больше `int64`.
Правка удаляла эти проверки и оставляла только вычитание (неканонический
ноль `sign == 0` с заведённым лимбом сохранялся).

Правка была реализована, измерена и **откачена**: выигрыш не подтвердился.

### 5.1 A/B по настоящей DLL (методика дня)

Две `laiue_numeric.dll` — до и после — чередовались, 15 пар, брались
минимум и медиана. `numeric_physics_benchmark`:

| операция | база min | после min | Δ min | база med | после med | Δ med |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `add_in_place.wide` | 3,314 | 2,887 | **−12,9 %** | 3,402 | 2,938 | **−13,6 %** |
| `add_in_place.small` | 1,896 | 1,773 | −6,5 % | 1,932 | 1,827 | −5,4 % |
| **контроль: `to_double.small`** (код не менялся) | 1,359 | 1,555 | **+14,4 %** | 1,378 | 1,577 | **+14,4 %** |
| контроль: `to_double.wide` (код не менялся) | 2,700 | 2,887 | +6,9 % | 2,822 | 2,928 | +3,8 % |
| остальные 12 операций | — | — | в пределах ±2,5 % | — | — | — |

Проблема видна сразу: **неизменённый** `to_double.small` уехал на +14 % —
столько даёт одна лишь перекладка кода в LTO-сборке. Эффект правки (−13 %)
неотличим от этого шума.

### 5.2 Контролируемый зонд в одном модуле трансляции

Чтобы убрать раскладку DLL, `build/peer/wide_probe.c` включает сам
`infinite_coord.c` под переименованным символом и сравнивает старую и новую
широкую функцию в одном бинарнике, обе `noinline`, на одинаковых входах
(5 пар заходов, 2 000 000 вызовов в серии):

| реализация | нс/вызов |
| --- | ---: |
| старая | 2,878 |
| новая | 3,115 |

Здесь новая оказалась **на 8 % медленнее**. Это, скорее всего, артефакт
встраивания помощника вычитания в одном варианте и не в другом, но важен
вывод: чистого ускорения нет, знак эффекта зависит от способа сборки.
Итог: выигрыш **не доказан**, по правилу «без выигрыша — не оставлять»
правка откачена. `git diff` пуст.

Фальсификация (до отката) подтвердила, что тесты держат это место:
удаление обработки `sign == 0` в новой широкой функции валило
`laiue_infinite_coord_test` сообщением «неканонический ноль сложился не как
раньше», а подмена знака после вычитания — «заём через границу лимба
построил не 2^64 − 1». То есть откат не оставил дыр в покрытии: 7799
прежних проверок на месте.

## 6. Проверка

- `ctest --preset windows-msvc-release --no-tests=error` — **30/30** до
  разведки, при отклонённой правке и после её отката. Золотые хеши
  детерминизма физики (`laiue.physics.determinism`) не менялись.
- `laiue_infinite_coord_test` — 7799 проверок, эталон на базе 2^32 не
  трогался.
- Правок API/ABI, CMake, глобальных или TLS-кэшей нет; итоговое дерево
  чистое.

## 7. Что осталось непроверенным

- Приложение (`simulation-of-sins/.../application.c`) вне разрешённого
  дерева; его собственный кадровый цикл не читался. Выводы о
  `panorama.c`/`camera.c` опираются на замер их цены и на то, что это
  прикладные экспорты, а не на подтверждённый профиль приложения.
- `audio_alsa.c` на Windows не исполнялся (Linux-бэкенд), его вклад оценён
  чтением кода.
- A/B микросекундных величин шумит на общей машине: `to_double.small`
  показывает, что перекладка кода даёт до ±14 %. Поэтому решения
  принимались только там, где эффект кратно больше шума; для широкого пути
  он таким не оказался.
- ARM64, clang и Linux-профили не запускались.

## 8. Вывод

Настоящая горячая точка среди непроверенных файлов одна —
`src/numeric/infinite_coord.c`. Её горячие входы (сложение на месте и
перевод в `double`) оптимизированы ранее, а оставшиеся операции по
детерминированным счётчикам холодные. Все прочие файлы списка на кадровом
или шаговом пути движка не встречаются: это загрузка контента, жизненный
цикл модов, построение шейдерных/текстурных/звуковых паков и
платформенные бэкенды. Единственная возможная правка в горячем файле
(широкий путь сложения) в честном A/B выигрыша не дала и откачена; итоговое
дерево не изменено.
