# Память стриминга чанков и правок мира: измерение и сокращение

Изолированное дерево `C:\Users\landi\projects\laiue-memworld`, ветка
`peer/memworld`. Зона — `src/scene/chunk_streaming.c` и
`src/world/world_infinite.c`; тесты — только добавление проверок в
существующие файлы. CMake, `src/physics/`, `src/render/`, `src/audio/` не
трогались.

**Итог.** Измерены четыре статьи памяти на радиусах 8/12/16 и на длинном
прогоне с правками. Найдены и исправлены две реальные потери:

1. **Таблица стриминга держала вторую таблицу на всю ёмкость**
   (`capacity` записей, до 3,5 МиБ на R=16) ради пересборки, которая на
   смене центра (телепорт) вообще не требует пересборки. Теперь телепорт
   вытесняет лишнее прямо в таблице, а для смены origin (где хеш ключей
   действительно меняется) осталась компактная арена ровно на гистерезисный
   куб `(2R+3)^3`. Экономия 0,51/0,70/1,21 МиБ на R=8/12/16 на весь сеанс.
2. **Опустевший после отката чанк мира оставался в таблице навсегда** вместе
   с буфером дельт на прежнюю пиковую ёмкость. Теперь запись с нулём дельт
   удаляется сдвигом кластера (без надгробий), как это уже делает стриминг.

Третий кандидат (очереди стриминга) отклонён с фальсификацией: запас поверх
активного куба нужен, чтобы ведущие грани шага помещались, пока не разобраны
заявки старого куба. Четвёртый пункт (буфер квадов) подтверждён численно, а
предпосылка о «второй копии» придержанного результата опровергнута — копия
одна, указатель переносится.

В `src/` изменены ровно два файла зоны, публичный API и ABI не трогались,
новых экспортов нет. Debug и Release: **30/30**. Состав и содержимое
загруженных чанков не меняются (доказательство и фальсификация в §7).

## 1. Стенд

Всё измерительное лежит только в `build/peer/` и в дерево не входит:

| файл | назначение |
| --- | --- |
| `build/peer/mem_stream_bench.c` | стенд: настоящий `ChunkStreaming` и `World`, фиктивный рендерер, зеркала внутренних раскладок, CSV |
| `build/peer/build_mem_bench.bat` | сборка стенда под Release (ключ `debug` — под Debug) |
| `build/peer/rebuild.bat` | сборка движка Debug+Release и `ctest` в обеих конфигурациях |
| `build/peer/build_one.bat` | сборка одной цели Debug |
| `build/peer/mem_baseline.txt` | вывод стенда до правок (Part A) |
| `build/peer/mem_after.txt` | вывод стенда после правок |

Стенд линкуется против уже собранных `laiue_*.lib` и работает с настоящими
DLL. Мир пуст, поэтому рабочие потоки строят ноль квадов и
`RendererCreateMesh` не вызывается — рендерер фиктивный. Внутренние
раскладки `ChunkStreaming` и `World` продублированы в стенде (как в
`chunk_streaming_stress_test.c` и в соаках), а живые размеры блоков сняты
`HeapSize(GetProcessHeap(), …)` — движок выделяет через
`HeapAlloc(GetProcessHeap())`, поэтому это точные занятые байты.

Проверки совпадения зеркал: `sizeof(ChunkEntry)=56`, `DrawItem=8`,
`ChunkRequest=40`, `ChunkMeshResult=48`, `Chunk=16`,
`GlobalChunkCoordinate=40`, и живое множество стриминга на каждом шаге
сверяется с независимым теневым кубом.

Размеры структур на x64 (MSVC, C17, `/W4 /WX`):

| структура | байт | из чего |
| --- | ---: | --- |
| `ChunkEntry` | 56 | x/y/z (24) + `mesh` (8) + `revision` (8) + `drawSlotPlusOne` (4) + `state` (4) + `requestQueued` (1) + выравнивание |
| `DrawItem` | 8 | `distanceSquared` + `entryIndex` |
| `ChunkRequest` | 40 | x/y/z (24) + `revision` (8) + `centerEpoch` (4) + выравнивание |
| `ChunkMeshResult` | 48 | x/y/z (24) + `quads` (8) + `revision` (8) + `quadCount` (4) + выравнивание |
| `Chunk` (мир) | 16 | `deltaCount` + `deltaCapacity` + `deltas*` |
| `GlobalChunkCoordinate` | 40 | `hash` + `frame*` + локальные x/y/z |

Приняты обозначения: `volume=(2R+3)³` — потолок гистерезиса,
`activeVolume=(2R+1)³` — активный куб,
`capacity=nextpow2(1.5·volume)` — ёмкость hash-таблицы мешей,
`queueCapacity=nextpow2(activeVolume)` — ёмкость каждого кольца очередей.

### 2.2. Плотность использования

Живых записей в устоявшемся состоянии после 600 случайных единичных шагов
(рабочие на паузе):

| R | живых на старте | максимум за прогулку | загрузка на максимуме | теоретический максимум (volume) | загрузка на нём |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 4913 | 5832 | 35 % | 6859 | 41,9 % |
| 12 | 15625 | 17576 | 53 % | 19683 | 60,1 % |
| 16 | 35937 | 39304 | 59 % | 42875 | 65,4 % |

Загрузка считается по ёмкости `capacity`. Целевой предел 2/3 (множитель
1,5) соблюдён; на R=8 фактическая загрузка всего 42 %, потому что
`1.5·volume = 10288` перешагивает 8192 и `nextpow2` даёт 16384. Уменьшить это,
не трогая хот-путь, нельзя: `FindEntry`/`InsertEntry`/`EraseEntry` работают на
маске (`& (capacity-1)`), а обратный сдвиг кластера в `EraseEntry` вообще
опирается на арифметику по модулю степени двойки. Переход на точную ёмкость
потребовал бы деления по модулю в каждом зондировании. Отклонено как
осознанный размен память↔скорость.

`drawItems` размером `volume`, а не `activeVolume`, тоже не запас:
после телепорта в гистерезисной оболочке радиуса +1 остаются меши, бывшие
внутри старого активного куба. Их число может превышать `activeVolume`, а
`volume` — точная верхняя граница (все живые в радиусе +1). Уменьшение
изменило бы множество загруженных чанков.

### 2.3. Что было лишним и что исправлено

Прежний код на смене центра больше чем на чанк (первый вызов, телепорт,
смена origin) делал так: `memset` второй таблицы на всю ёмкость, обмен
`entries`↔`spareEntries`, перезаливка живущих в новую таблицу. Вторая
таблица на `capacity` записей (917 КиБ … 3,5 МиБ) висела **весь сеанс**.

Ключевое наблюдение: хеш ключа чанка — `WorldHashChunkCoordinate(x,y,z)` —
не зависит от центра. Значит, при смене центра дом каждой оставшейся записи
не меняется, и пересборка в свежую таблицу не нужна: достаточно вытеснить
записи за пределами радиуса +1 прямо на месте. Добавлена
`PruneEntriesOutsideRadius`: она идёт по таблице, уничтожает меши ушедших
чанков, снимает их со списка отрисовки и удаляет `EraseEntry` (обратный сдвиг
кластера, без надгробий). Индекс не увеличивается после удаления — на место
дыры встаёт сдвинутая запись, её и надо разобрать тем же индексом.

Для `ChunkStreamingResumeAfterOriginChange` пересборка всё же нужна: origin
меняет абсолютные координаты живущих, а с ними и хеш. Но приёмником служит
компактная арена `rebuildScratch` ровно на `volume` записей: живых в
радиусе +1 больше `(2R+3)^3` не бывает. Она же заменяет прежнюю вторую
таблицу, поэтому `spareEntries` как отдельная сущность исчез.

Асимптотика не хуже прежней: и там, и тут проход по таблице O(capacity),
но исчез `memset` второй таблицы на `capacity·56` байт — трафик памяти на
телепорте упал, а не вырос. Точечный путь шага на соседний чанк не менялся.

## 3. Пункт 2. Дельты правок мира

### 3.1. Устройство и стоимость

`World` хранит правки по чанкам в отдельной открытой таблице:
`GlobalChunkCoordinate[]` + `Chunk*[]` + `bool[]`. У чанка — `Chunk`
(16 Б) и буфер `DeltaEntry` (по 4 Б на правку, ёмкость удваивается с 4).
Таблица растёт при `count·2 ≥ capacity`, то есть несёт примерно
`2·(40+8+1)=98` Б накладных на чанк плюс 16 Б структуры, плюс дельты.

### 3.2. Долгий прогон

Прогон: мир без провайдера, правки по расширяющейся спирали чанков, по
4 правки в чанк. Точки — раз в 6400 чанков; всего 64 000 чанков и 256 000
правок, затем откат половины и повторная правка, затем телепорт стриминга
на (5000,5000,5000). `procPrivate` — `PrivateUsage` процесса, шумит от
работы аллокатора; детерминированные байты важнее.

| фаза | чанков с правками | таблица, Б | структуры чанков, Б | дельты, Б | всего, Б | procPrivate, Б |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 6 400 | 6 400 | 802 816 | 102 400 | 102 400 | 1 007 616 | 58 875 904 |
| 12 800 | 12 800 | 1 605 632 | 204 800 | 204 800 | 2 015 232 | 59 576 320 |
| 32 000 | 32 000 | 3 211 264 | 512 000 | 512 000 | 4 235 264 | 62 402 560 |
| 64 000 | 64 000 | 6 422 528 | 1 024 000 | 1 024 000 | 8 470 528 | 67 588 096 |
| после отката половины | 32 000 | 6 422 528 | 512 000 | 512 000 | 7 446 528 | 67 588 096 |
| после повторной правки | 64 000 | 6 422 528 | 1 024 000 | 1 024 000 | 8 470 528 | 67 588 096 |
| центр ушёл на (5000,5000,5000) | 64 000 | 6 422 528 | 1 024 000 | 1 024 000 | 8 470 528 | — |

Выводы:

- Память под дельты растёт **линейно числу чанков с правками**, а не
  времени: 64 000 чанков по 4 дельты дают ровно `64000·(16+16)=2 048 000` Б
  буферов и структур (плюс high-water таблицы).
- После ухода стриминга в другую часть мира (все чанки выгружены из
  радиуса обзора) дельта-память **не меняется**. Это и есть ожидаемый
  компромисс: мир обязан помнить правки, чтобы при возврате в ту же
  абсолютную точку показать то же самое. Если бы правки терялись при
  выгрузке, сломалось бы само понятие правки в бесконечном мире. Это не
  утечка, а необходимое состояние.
- Ёмкость таблицы ключей `WorldGrow` только растёт (high-water). После
  отката половины правок таблица остаётся 6,4 МиБ, хотя чанков вдвое
  меньше. Это тот же приём, что у пула рендера: пик сеанса не отдаётся
  обратно. Уменьшение таблицы потребовало бы перехеширования на каждом
  удалении; отклонено.

### 3.3. Найденная потеря: пустые чанки

Была реальная утечка «в ноль»: `WorldTrySetBlock(..., base)` в чанке с
одной последней дельтой вызывал `ChunkRemoveDelta`, но запись оставалась в
таблице навсегда — с буфером дельт на пиковую ёмкость. Игрок, который
построил и снёс постройку, оставлял по 32 Б (16 структуры + 16 дельт при
пике 4) на каждый такой чанк, плюс слот в таблице.

Исправление: `WorldEraseChunkAt` (обратный сдвиг кластера, как `EraseEntry`
в стриминге) удаляет запись целиком, когда `deltaCount` стал нулём —
и в одиночном пути, и в публикации батча (`stagedCount == 0`). Отдельного
API/экспорта не добавлено, функция статична.

Макротест B2: 100 правок в один чанк.

| момент | чанков | дельта-байт | `deltaCapacity` | `deltaCount` |
| --- | ---: | ---: | ---: | ---: |
| после 100 правок | 1 | 512 | 128 | 100 |
| полный откат **до** правки | 1 | 512 | 128 | 0 |
| полный откат **после** правки | **0** | **0** | 0 | 0 |

На длинном прогоне откат половины из 64 000 чанков освобождает
**1 024 000 Б** (32 Б × 32 000), повторная правка возвращает их обратно.

Что отклонено: выгружать **непустые** дельты при вытеснении чанка из
радиуса стриминга. Это потеряло бы правки и сломало бы возврат в ту же
точку; правки — не кеш, а состояние мира. Рост под них оправдан числом
реально изменённых мест, а не временем.

## 4. Пункт 3. Очереди стриминга

`requests` и `results` рассчитаны на `queueCapacity`, а не на весь
гистерезисный куб. Вместе они стоят:

| R | activeVolume | queueCapacity | запас (слотов) | requests+results, Б | было бы при точной ёмкости |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 4913 | 8192 | 3279 | 720 896 | 432 344 (−288 552) |
| 12 | 15625 | 16384 | 759 | 1 441 792 | 1 375 000 (−66 792) |
| 16 | 35937 | 65536 | 29599 | 5 767 168 | 3 162 456 (−2 604 712) |

На первый взгляд округление до степени двойки — чистый запас. Оно
**проверено на фальсификацию**: точную ёмкость `activeVolume` я поставил
(с кольцом по модулю) и получил падение существующего теста
`laiue.scene.voxel_raycast`:

> `Voxel raycast check failed: a diagonal step must request exactly the two leading faces`

Причина содержательная. На диагональном шаге в таблицу добавляются две
ведущие грани, но заявки старого куба (рабочие на паузе) ещё не разобраны, и
`unfinishedWork` уже равен `activeVolume`. Точное кольцо не даёт места новым
заявкам; они ушли бы в retry, и накопительный счётчик заявок перестал бы
совпадать с геометрией шага. Округление вверх даёт запас на ведущие грани (и
заодно маску вместо деления). Правка откачена.

Итог: ёмкость очередей не «завышена», а несёт запас на переходный процесс
шага; это подтверждено конкретным тестом, а не рассуждением. Отклонено.

## 5. Пункт 4. Буфер квадов меша

`ChunkQuad` — 8 Б. Мешер выделяет `faceCount` квадов, затем сжимает
`PlatformReallocate` до `quadCount`; копии хвоста нет. Измерено:

| сценарий | квадов | `quads`, Б | `ChunkMeshResult`, Б | буфер «в полёте», Б |
| --- | ---: | ---: | ---: | ---: |
| гладкий рельеф | 222 | 1 776 | 48 | 1 824 |
| шероховатый рельеф | 9 670 | 77 360 | 48 | **77 408** |
| шахматка (worst case) | 786 432 | 6 291 456 | 48 | **6 291 504** |

Гладкий и шероховатый рельефы дают 1,8 КБ и 77 КБ — второй близок к
«порядка 100 КБ на меш» из `docs/streaming_soak_parallel_work.md`.
Верхняя граница — шахматка: greedy не сливает ни одной грани, `quadCount`
доходит до `3·64³ = 786 432`, буфер — 6 МиБ. Это ровно тот размер, который
нужно удержать на один кадр при отложенной загрузке.

**Предпосылка о «второй копии» придержанного результата неверна.**
`ChunkStreamingPump` вынимает `ChunkMeshResult` из кольца по значению и в
случае отказа рендера делает `streaming->heldResult = result` — то есть
**переносит указатель** `quads`, а освобождение делает только при
`!holdResult`:

```c
if (result.quads != NULL && !holdResult) PlatformFree(result.quads);
```

`TryUploadHeldResult` передаёт `held->quads` в `RendererCreateMesh` и
освобождает их после. Значит, на лишний кадр живёт **та же одна** копия
геометрии, а не вторая. Дополнительных 48 Б структуры — не копия буфера.
Лишнего копирования нет, чинить нечего.

## 7. Доказательство неизменности и фальсификация

**Стриминг.** `PruneEntriesOutsideRadius` удаляет ровно те записи, которые
прежняя пересборка отбрасывала (за пределами радиуса +1), и сохраняет у
оставшихся те же поля (`state`, `revision`, `requestQueued`, `mesh`); меши
ушедших уничтожаются ровно те же. `ChunkStreamingResumeAfterOriginChange`
собирает тот же набор (меш есть и координата после вычитания дельты в
радиусе +1), уничтожает тех же и вставляет с новыми ревизиями, как раньше.

Фальсификация — независимый теневой куб в
`tests/chunk_streaming_stress_test.c`: после **каждого** шага (случайные
шаги, круг, телепорты, смена origin, многопоточный сценарий) множество
ключей таблицы сверяется с эталоном по геометрии, а в Debug дополнительно
исполняется `VerifyStreamingIntegrity` (достижимость каждого ключа,
отсутствие дубликатов, согласованность списка отрисовки и колец). Если
вытеснение на месте потеряло бы или лишний раз сохранило запись, тест
упал бы. Debug и Release — проходят.

**Мир.** `WorldEraseChunkAt` вызывается только когда `deltaCount == 0`, то
есть `WorldGetBlock` и до, и после возвращает базовое значение — содержимое
мира не меняется. Обратный сдвиг не должен рвать цепочки пробирования
уцелевших соседей. Фальсификация — новый тест
`TestEmptyChunkRemovalBackwardShift` в `tests/world_provider_test.c`:
512 чанков по 3 правки в разных слотовых позициях, затем откат **каждого
второго** чанка (удаление) и проверка, что каждая уцелевшая правка читается,
а каждая откаченная — нет; плюс ветка батча с полным откатом. При потере
соседа по кластеру уцелевшая правка стала бы недостижимой и тест упал бы.
