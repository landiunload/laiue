# Устранение полной пересборки hash-таблицы чанков на переходе

Работа велась в изолированном дереве `C:\Users\landi\projects\laiue-table`,
ветка `peer/table`. Зона — только `src/scene/chunk_streaming.c`. Публичный
API/ABI, заголовки, CMake, `world/mesh/render/physics` не менялись.

Итог: полная пересборка таблицы на каждом шаге на соседний чанк заменена
точечным удалением ушедших граней и вставкой пришедших. Детерминированные
счётчики совпали с прежними до последней единицы, время `SetCenter` на
R=8..16 упало примерно в 4–5 раз (по минимуму — на 77–82 %). Проверка
целостности, написанная до правки, поймала **реальную причину**
повреждения кучи, из-за которой предыдущая попытка была откачена; после
исправления этой причины повреждение не воспроизводится ни в Release, ни
в Debug.

## 1. Что и почему менялось

`ChunkStreamingSetCenter` на переходе ровно на соседний чанк
(`|delta| <= 1` по каждой оси) делал полную пересборку открытой
hash-таблицы: `memset` запасного массива и повторная вставка `≈(2R+3)³`
записей. При этом меняются только уходящие грани старого куба (радиус
`R+1`) и дальние грани нового (радиус `R`), то есть `O((2R+1)²)` записей
против `O(capacity)`.

Теперь для такого перехода:

1. `EvictDepartedChunks` перебирает только уходящие грани — по одной на
   каждую ось, изменившую знак (для диагонали их две-три). Для каждой
   ячейки `EvictChunk` снимает меш со списка отрисовки, освобождает его и
   удаляет запись из таблицы.
2. `QueueMissingLeadingFace` (уже был в дереве) заказывает дальние грани.
3. Таблица не `memset`-ится и не перезаливается; список отрисовки не
   сбрасывается целиком.

Первый вызов, телепорт и смена origin по-прежнему идут по полному пути
(`QueueMissingChunks` + пересборка таблицы) — их частота не менялась.

### Удаление из открытой адресации

Выбрана чистка сдвигом кластера, а не надгробия: надгробия со временем
набивают таблицу (при блуждании центра посещённых ключей неограниченно
много), и её пришлось бы периодически пересобирать. `EraseEntry`
реализует классический backward-shift: после удаления сканирует кластер
вперёд и переносит элемент в дыру только если дыра лежит на его пути
пробирования (`(hole-home) & mask <= (scan-home) & mask`); иначе элемент
остаётся, а дыра «уезжает» дальше и в конце кластера становится `EMPTY`.

## 2. Проверка целостности

В `chunk_streaming.c` добавлена `VerifyStreamingIntegrity`, вызываемая в
конце `ChunkStreamingSetCenter` (оба пути) и
`ChunkStreamingResumeAfterOriginChange`. Она компилируется только при
`#ifndef NDEBUG`, поэтому в Release её нет. Проверяет:

- **таблицу**: для каждой занятой записи её ключ действительно находится
  `FindEntry` именно в этом слоте; по пути пробирования до слота нет
  `EMPTY` (иначе запись «потеряна»/недостижима) и нет другого слота с тем
  же ключом (дубликат);
- **список отрисовки**: каждый `drawItems[i].entryIndex` в диапазоне,
  указывает на запись с непустым мешем, `drawSlotPlusOne == i+1`,
  `FindEntry` для неё возвращает ровно эту запись; и обратно — у каждой
  записи с мешем есть слот, и он указывает на неё;
- **кольца заявок/результатов**: `requestCount`, `resultCount`,
  `unfinishedWork` не превышают ёмкость, и
  `unfinishedWork >= requestCount + resultCount` (в работе не может быть
  отрицательного числа заявок).

При провале печатается причина и выполняется намеренное обращение по
нулевому указателю — тест падает с внятным сообщением, а не молча.

На нынешнем (исходном) коде проверка проходит, и — что важнее — на новой
правке она тоже проходит на всех сценариях ниже.

## 3. Причина прежнего повреждения кучи (главное)

Таблица — открытая адресация, а `DrawItem` хранит **индекс** в массиве
`entries` (`entryIndex`), а не указатель. Сдвиг кластера при удалении
перемещает `ChunkEntry` в массиве, а индекс в `drawItems` остаётся старым.
Дальше `RemoveMeshFromDrawList` / `AddMeshToDrawList` / `ChunkStreamingDraw`
работают с чужой (или пустой) записью: `RendererDestroyMesh` вызывается
для чужого/повторно освобождённого `RendererMesh` — это и есть
`STATUS_HEAP_CORRUPTION` «при создании мешей».

Причина подтверждена экспериментом: если убрать единственную строку,
чинящую ссылку (`drawItems[moved->drawSlotPlusOne - 1].entryIndex = hole`),
Debug-стенд падает с

```
chunk streaming integrity: draw item references an entry without mesh
```

То есть без проверки целостности эта правка снова привела бы к
повреждению кучи. В итоговом коде ссылка чинится для каждого
перемещённого элемента, и проверка больше не срабатывает.

## 4. Фальсификация

Для каждой оставленной правки внесена намеренная поломка и подтверждено,
что проверка её ловит (Debug-сборка со включённой проверкой):

| поломка | сообщение проверки |
| --- | --- |
| убрать чистку `drawItems[...].entryIndex` при сдвиге | `draw item references an entry without mesh` |
| `EraseEntry` без сдвига (просто `EMPTY` в дыру) | `entry unreachable through FindEntry` |
| убрать `FindEntry`-проверку в `QueueChunkIfMissing` | `duplicate chunk key in table` |

Все три поломки возвращены; после возврата проверка и полный CTest снова
проходят. Исходная проверка (пункт 2) ловит потерянную запись, дубликат
ключа и запись, недостижимую через `FindEntry`, — как и требовалось.

## 5. Детерминированные счётчики

Стенд `build/peer/stream_probe.c` (в дерево не входит) с настоящим
D3D12-рендерером в скрытом окне, настоящим мешером и счётчиком обращений
к провайдеру. Режим `run`: центр шагает по +X, после каждого шага
рабочие доводятся до конца (`Pump` до пустых очередей). Один и тот же

единственные выделения — буфер квадов мешера и `RendererMesh` рендера,
как и раньше (они в зоне других модулей).

## 6. Время `SetCenter`

Измерение на паузе рабочих (в таблице живут `PENDING`-записи, меши не
создаются), `time <R> 256 64`: 256 переходов, первые 64 — прогрев,
считаются следующие 192. Три чередующихся раунда `before/after`; машина
общая, поэтому приведён **минимум** (и разброс средних).

| R | до, мин (диапазон средних / шаг), мкс | после, мин (диапазон средних), мкс | выигрыш по минимуму |
| ---: | ---: | ---: | ---: |
| 8 | 52,4 (57,7–60,1) | **12,2** (20,9–22,7) | −77 % |
| 12 | 181,4 (202,4–212,6) | **36,4** (64,6–68,0) | −80 % |
| 16 | 413,7 (462,6–485,2) | **74,8** (109,5–149,5) | −82 % |

Убранная работа — это ровно `memset` + повторная вставка `≈(2R+3)³`
записей; остаётся обход уходящих/приходящих граней, поэтому выигрыш
растёт с радиусом.

## 8. Ограничения и честные оговорки

- Только Windows x64, MSVC 19.44, D3D12, Release/Debug. clang-cl, ARM64,
  Linux/macOS и санитайзеры не запускались; Vulkan не проверялся (SDK
  нет), но `ChunkStreaming` от бэкенда не зависит.
- Тесты не трогались: `tests/voxel_raycast_test.c` уже проверяет счёт
  заявок при переходах, и он проходит. Новый проверочный код —
  внутренний и включается только в `!NDEBUG`; CMake не менялся.
- **Порядок в списке отрисовки.** Правка не сбрасывает список целиком, а
  поддерживает его точечно (`Add/RemoveMeshFromDrawList`). Итоговый
  порядок выдачи задаётся сортировкой по расстоянию в
  `ChunkStreamingDraw`, и множество выданных чанков не меняется;
  счётчики совпали. Прежний код перед каждой сортировкой заново
  наполнял список в порядке индексов пересобранной таблицы, новый — в
  порядке текущего массива. Для чанков с **разными** расстояниями
  результат сортировки идентичен; при точном равенстве расстояний
  heap-сортировка не устойчива, и порядок равных по дальности чанков
  теоретически может отличаться. Точное совпадение этого порядка
  несовместимо с отказом от пересборки таблицы: индексы записей в
  пересобранной и не пересобранной таблице разные. В проверяемых
  детерминированных сценариях это не наблюдалось.
- Долгосрочная насыщенность таблицы не растёт: сдвиг не оставляет
  надгробий, число живых записей ограничено кубом радиуса `R+1`, под
  который и посчитана ёмкость. Пересборка нужна только на первый
  вызов/телепорт/origin, как и раньше.
