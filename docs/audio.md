# Аудио

`laiue_audio` — микшер голосов с низкой задержкой. Устройство владеет
одним потоком вывода и смешивает в него активные голоса; приложение
управляет голосами из своих потоков и никогда не блокирует поток вывода.

Микшер, системный вывод и загрузчик содержимого — независимые providers.
`laiue_audio.dll` (или `liblaiue_audio.so`) публикует сервис `laiue.audio`, а
`laiue_audio_output.dll` / `liblaiue_audio_output.so` публикует необязательный
`laiue.audio.output`. Микшер всегда содержит offscreen-вывод и при старте
берёт таблицу системного provider-а, если тот выбран профилем. Поэтому
удаление output DLL отключает только системный звук: offscreen, диагностика и
остальные технологии продолжают работать. `laiue_audio_pack.dll` публикует
`laiue.audio.pack` и получает сервисы
`laiue.audio` и `laiue.assets` через bootstrap ABI. Новый pack-provider не
импортирует ни одну DLL LAIUE: если его файл отсутствует, звукопаки просто
недоступны; если отсутствует mixer, bootstrap сообщает о неудовлетворённой
зависимости, а остальные технологии продолжают работу. Прямой вызов
загрузчика из приложения больше не является отдельной реализацией: приложение
получает таблицу `laiue.audio.pack` через bootstrap и вызывает её функции.

Вывод provider-а на Windows — WASAPI в общем режиме с событийной подачей, на Linux —
ALSA, на Android — AAudio, на macOS и iOS — выходной AudioUnit
(DefaultOutput и RemoteIO). ALSA выбрана потому, что PipeWire и PulseAudio
предоставляют совместимый ALSA-выход: одна зависимость покрывает и обычный
десктоп, и Steam Deck. AAudio — штатный путь Android с низкой задержкой; как
и AudioUnit, он сам вызывает заполнение буфера на realtime-потоке системы,
что совпадает с контрактом микшера. Бэкенд выбирается при сборке, а
наружу всегда отдаётся одна таблица `laiue.audio.output`, поэтому модуль
по-прежнему удаляется целиком. Задержка равна периоду устройства — обычно
около 10 мс.

## Границы модуля

Движок отвечает за вывод, смешивание, громкость, панораму и скорость
воспроизведения. Всё остальное принадлежит приложению:

- расстояние, затухание, реверб и прочая пространственная политика —
  приложение вычисляет громкость и панораму само, ровно как вычисляет
  свет для рендера;
- разбор контейнеров — внутренняя `media_support`; клипы по-прежнему
  получают готовый PCM16, а отдельный потоковый путь вызывает тот же
  собственный WAV/MP3-декодер небольшими блоками;
- приоритет голосов — при исчерпании лимита выдача честно отказывает и
  не обрывает уже звучащее.

`AudioClip` остаётся обычным быстрым путём для эффектов. Потоковое
воспроизведение выбирается явно через `AudioStream`; оно экономит память
длинных треков ценой декодирования, I/O и дополнительных проверок кольца.
Звукопаки и `.la` пока загружаются целиком прежним путём. Встроенного
сетевого транспорта, AAC и HTTP-плеера нет.

## Модель

| Понятие | Смысл |
|---|---|
| `AudioDevice` | микшер и выбранный вывод; один поток provider-а на устройство |
| `AudioClip` | декодированные сэмплы в памяти, переживают свои голоса |
| `AudioStream` | ограниченный буфер и состояние WAV/MP3-декодера с одним курсором |
| `.lap` | звукопак: каталог со звуками, заменяемый целиком |
| `AudioVoice` | дескриптор звучащего экземпляра клипа |

Клип можно разрушить и во время звучания: движок сам остановит его
голоса, а память освободит тогда, когда поток вывода на неё больше не
смотрит — тем же отложенным освобождением, каким рендер отпускает
диапазоны геометрии. Порядок «сначала остановить, потом разрушить»
остаётся предпочтительным: он не обрывает звук на середине.

Дескриптор голоса содержит номер слота и поколение. Поколение растёт при
каждом переиспользовании слота, поэтому устаревший дескриптор нельзя
случайно применить к чужому звуку: `AudioVoiceSetParameters` вернёт
`false`, а `AudioVoiceStop` ничего не сделает.

Остановка голосов асинхронна. `AudioDeviceStopAllVoices` принимается и при
переполненной очереди обычных команд; успешно принятый последующий `Play`
остаётся после этой остановки. Повторная остановка без новых команд может
объединяться с уже ожидающей. `activeVoices` описывает завершённый буфер,
а не подтверждает выполнение только что отправленной команды. В offscreen
режиме ожидающие команды применяются при следующем `RenderFrames`.

## Минимальный цикл

```c
AudioDevice* device = NULL;
if (AudioDeviceCreate(NULL, &device) != AUDIO_RESULT_OK)
{
    return;   // звукового устройства нет
}

AudioClipDescription description = {
    .samples = pcmSamples,      // int16, чередование по каналам
    .frameCount = frameCount,
    .channelCount = 1u,
    .sampleRate = 44100u,
};
AudioClip* clip = NULL;
AudioClipCreate(device, &description, &clip);

AudioVoiceParameters parameters = {
    .volume = 0.8f, .pan = -0.3f, .speed = 1.0f, .looping = false,
};
AudioVoice voice = AudioVoicePlay(device, clip, &parameters);
if (voice == AUDIO_VOICE_NONE)
{
    // Свободных голосов нет; звук пропущен осознанно.
}

AudioVoiceStop(device, voice);
AudioClipDestroy(clip);
AudioDeviceDestroy(device);
```

Готовый звук из активного звукопака загружается одной строкой; всё
остальное — то же самое:

```c
AudioPackLoadStatus status = AUDIO_PACK_LOAD_NOT_ATTEMPTED;
AudioClip* step = AudioClipLoadFrom(device, catalog, L"step", &status);
```

## Длинные треки

`audio/audio_stream.h` добавляет WAV/MP3, pause/resume, seek, позицию и
статистику. Пауза и перемотка доступны также для обычных клипов:

```c
AudioStream *music = NULL;
if (AudioStreamOpenFile(device, "music/theme.mp3", &music) == AUDIO_RESULT_OK)
{
    AudioVoice voice = AudioVoicePlayStream(device, music, NULL);
    AudioVoicePause(device, voice, true);
    AudioVoiceSeek(device, voice, 30.0);
    AudioVoicePause(device, voice, false);
    double seconds = 0.0;
    AudioVoiceGetPosition(device, voice, &seconds);
    // По окончании или при смене трека:
    AudioStreamDestroy(music);
}
```

К потоку привязан один активный голос; второй одновременный курсор требует
отдельного `AudioStream`. Повторный запуск остановленного или завершённого
потока начинается с нуля и выдаёт новый дескриптор. Поток принадлежит
устройству, чужое устройство не может его воспроизводить. `AudioStreamDestroy`
останавливает его голос и worker, закрывает источник и откладывает
освобождение PCM-кольца до обработки уже опубликованных команд и завершения
микширования. Даже заполненная очередь команд и пауза не препятствуют
остановке. Без новых вызовов вывода память кольца сохраняется до разрушения
устройства; destroy не ждёт callback-а вывода. `AudioDeviceDestroy` сначала
останавливает output, затем joins всех workers и освобождает оставшиеся
потоки. После него указатели на потоки недействительны.

Файл открывается один раз, читается по смещениям и остаётся открытым до
закрытия источника. Для собственной файловой системы есть
`AudioStreamCreate` с `AudioStreamDescription{structSize, context, readAt,
close, sizeBytes}`. `readAt` обязан полностью заполнить запрошенный диапазон
или вернуть 0. Ownership `context` передаётся только при успешном create;
`close`, если задан, вызывается ровно один раз, после прекращения чтения.
Неуспешный create оставляет источник вызывающему. Callback-и исполняются
последовательно из decoder worker или вызывающего API/offscreen потока и
не должны повторно входить в API того же устройства.

Для системного вывода каждый поток имеет decoder worker. Он заполняет
восемь заранее выделенных блоков по 1024 исходных кадра; MP3 хранит один
MPEG-кадр PCM, битовый резервуар, overlap и состояние фильтров. WAV читает
порции до 16 КиБ. Ни весь файл, ни полный PCM-трек, ни растущий индекс
смещений не выделяются. Open MP3 проходит заголовки кадров для определения
длительности; WAV пропускает payload и читает заголовки чанков. Offscreen
вывод заполняет кольцо на вызывающем потоке между ограниченными порциями
рендера, что даёт воспроизводимые тесты и готовый первый буфер после seek.
Callback системного микшера не выделяет память, не читает файл, не логирует
и не захватывает decoder/application lock.

Pause/resume и seek становятся слышимыми при обработке команды в следующем
буфере вывода. Пауза сохраняет позицию и активный голос. Seek проверяет
диапазон `[0, duration]`, округляет вниз до исходного кадра и подготавливает
decoder на вызывающем потоке. Для MP3 это точный replay от начала, включая
резервуар и историю синтеза: время растёт с целевой позицией, память
остаётся постоянной. Частые большие seek следует выполнять на прикладном
рабочем потоке. Для WAV seek меняет смещение за постоянное время. Новая
позиция публикуется, когда output применил команду; запрос возвращает
исходные секунды, с учётом speed и повторов. Seek на конец завершает
неповторяющийся голос; при loop он начинает новый круг. Переполненная
очередь отклоняет seek до изменения decoder. При недостатке готового PCM
системный output отдаёт тишину и сохраняет позицию; `underruns` показывает
такие буферы. Ошибка дальнейшего чтения отражается в `result` статистики и
завершает голос после уже подготовленных кадров.

Поддерживается тот же набор форматов, что у полного декодера: mono/stereo,
PCM WAV 8/16/24/32 бит и IEEE float WAV 32/64 бит; MPEG-1 Layer III MP3
32/44,1/48 кГц, VBR/CBR и trim LAME. MPEG-2/2.5, другие Layers и free format
отклоняются. Сохраняются общие ограничения reader-а: не более 2³²−1 байт
источника и 2²⁶ слышимых исходных кадров. Это локальный random-access stream,
а не обещание воспроизводить произвольный сетевой источник.

`AudioStreamStats.memoryBytes` считает выделенные самим потоком heap buffers
(описатель, кольцо, decoder scratch). На Windows x64: WAV — 49 632 байта,
MP3 — 116 856 байт для callback-источника, одинаково для короткого звука и
пяти минут музыки. Встроенный file source добавляет 16 байт описателя файла. Для
сравнения, пять минут stereo PCM16 при 48 кГц — 57 600 000 байт
(54,93 МиБ). Счётчик не включает внешний `context`, общий `AudioDevice`,
backend, allocator overhead и резерв виртуального стека OS worker; он не
является измерением RSS процесса. `bufferedFrames` — консервативная верхняя
оценка, максимум 8192, а не точная сумма незвучавших кадров.

Ручной `benchmarks/audio_stream_benchmark.c` сравнивает готовый PCM с
потоковым WAV из памяти: один повторяющийся голос, mono/stereo, 48 кГц,
volume 1, pan −1, speed 1; 10 000 буферов по 256 кадров (2 560 000 кадров)
на выборку, один полный прогрев, затем семь пар PCM → stream. Создание и
allocation вне замера; checksum готового буфера сверяется после каждого
прохода. Печатаются raw timings, median и ns/frame; performance assertions
и автоматического CTest-запуска нет.

На AMD Ryzen 7 8700F (8 ядер / 16 потоков), Windows x64, MSVC 19.51.36260,
Release AVX2 получены следующие времена. Exact compile flags харнесса:
`/DWIN32 /D_WINDOWS /O2 /DNDEBUG /std:c17 /MD /W4 /utf-8 /GS- /WX /Ot /Oi
/GF /Gy /Gw /volatile:iso /Zc:inline /arch:AVX2 /Ob3 /GL`; mixer DLL —
`windows-msvc` Release из того же worktree. Линковка харнесса —
`/NODEFAULTLIB /LTCG /ENTRY:AudioStreamBenchmarkEntryPoint /SUBSYSTEM:CONSOLE`
с `laiue_audio`, `laiue_platform_support` и no-CRT runtime проекта.

| Сценарий | Raw PCM, мкс за 2 560 000 кадров | Raw WAV stream, мкс за 2 560 000 кадров |
|---|---|---|
| Mono | 546, 479, 451, 611, 445, 453, 489 | 9065, 10121, 9233, 10662, 8623, 9243, 9773 |
| Stereo | 657, 508, 604, 516, 915, 516, 879 | 12794, 11133, 11677, 11303, 12091, 15074, 13511 |

Медианы: mono PCM 479 мкс / stream 9243 мкс (0,187 / 3,610 нс на кадр);
stereo PCM 604 мкс / stream 12 091 мкс (0,236 / 4,723 нс на кадр).
Относительно этого очень дешёвого PCM-пути stream дороже в 19,30 / 20,02
раза (+1829,6% / +1901,8%). Абсолютная стоимость stream — 0,924 / 1,209 мкс
на буфер из 256 кадров. Это стоимость всего offscreen decode+mix пути WAV
с `memcpy`-источником; она не оценивает дисковый I/O, MP3, системный output
или worker scheduling. Обычный PCM выбран по умолчанию и не заменён этим
путём. Итоговый checksum стенда: `10604107594001403779`.

Для повторения после включения ручного target-а:

```powershell
cmake --build --preset windows-msvc-release --target laiue_audio_stream_benchmark
build/windows-msvc/bin/Release/laiue_audio_stream_benchmark.exe
```

Новые функции добавлены после `context` в хвост `LaiueAudioServiceV1`;
версия 1 и прежние смещения сохранены. Клиент проверяет обе границы:
`LaiueAudioServiceV1HasStreaming(audio, tableSize)` учитывает host-reported
размер, `structSize` и наличие функций. Старые клиенты запрашивают
`LAIUE_AUDIO_SERVICE_V1_LEGACY_SIZE` или `_CONTEXT_SIZE` и используют только
известные поля. Новый клиент при отсутствии хвоста может оставить свой
обычный путь с клипами.

## Потоки

Поток вывода не берёт ни одной блокировки, которую держит приложение.
Команды идут через кольцо с одним потребителем: приложение публикует
запись, поток вывода разбирает накопленное в начале каждого буфера.
Состояние голоса после старта принадлежит только потоку вывода.

Между собой потоки приложения разводит внутренний мьютекс, поэтому
`AudioVoicePlay` и остальные вызовы можно делать из нескольких потоков.
Если приложение отправляет команды быстрее, чем поток вывода их
разбирает, лишние отбрасываются, а счётчик `droppedCommands` в
`AudioDeviceGetStats` это показывает.

## Проверка без звукового устройства

`AUDIO_BACKEND_OFFSCREEN` создаёт устройство без вывода: кадры отдаёт
`AudioDeviceRenderFrames` из внутреннего `audio/audio_offscreen.h`. Это
делает микшер проверяемым по сэмплам на машине без звуковой карты и в
контейнере CI. `laiue.audio.mixer` проверяет обычные клипы;
`laiue.audio.streaming` — образцы PCM, loop, pause, скорость, seek при полном
кольце, несколько seek до ACK, переполнение команд, ownership и разрушение
worker-а через подставной системный output. `laiue.media.sound_stream`
сверяет блоки и seek с полным декодером для всех WAV-разрядностей и
реального MP3 с trim и reservoir. Длинные виртуальные источники проверяют
постоянство workspace и предел размера отдельного чтения.

Системный вывод проверяет отдельный `laiue.audio.system_backend`: он
беззвучен (общая громкость ноль, голосов нет) и убеждается, что
устройство открылось и его поток действительно тянет кадры. Там, где
устройства нет, тест сообщает о пропуске, а не о провале.

ALSA загружается в рантайме, а не линкуется, поэтому её отсутствие не
мешает ни собрать модуль, ни загрузить его: микшер и его тесты от вывода
не зависят, а запрос системного бэкенда честно вернёт
`AUDIO_RESULT_BACKEND_INITIALIZATION_FAILED`. Заголовки ALSA не нужны и
на сборке — нужные типы и константы объявлены в самом модуле.

Перед выгрузкой libasound провайдер освобождает её глобальный кэш
конфигурации (`snd_config_update_free_global`, если символ есть). Иначе
`dlclose` уносил указатель на дерево вместе с библиотекой, и каждый цикл
создания вывода терял около 100 КиБ даже при неудачном открытии
устройства; `laiue.audio.output_cycle` проверяет это по RSS без звуковой
карты.

На мобильных и консольных профилях системный provider может быть заменён
платформенным адаптером или отключён полностью. Offscreen-вывод и таблица
`laiue.audio` остаются тем же C ABI; в статической сборке оба provider-а
регистрируются
через тот же module registry, без обязательной загрузки DLL.

## Зависимости

| Платформа | На линковке | В рантайме |
|---|---|---|
| Windows `audio_output` | `ole32`, `avrt` | — |
| Linux `audio_output` | — | `libasound.so.2`, необязательна |
| Android `audio_output` | — | `libaaudio.so` (Android 8.0+), необязательна |
| macOS/iOS `audio_output` | `AudioToolbox.framework` | — |

AAudio, как и ALSA, открывается через `dlopen`: статическому приложению не
нужно добавлять `-laaudio` в финальную линковку, а отключение устройства
(наушники, Bluetooth) увеличивает счётчик опустошений, по которому
приложение пересоздаёт вывод. Вывод Android проверен сборкой NDK r29, Apple —
сборкой в CI; на реальных устройствах в CI они не запускаются.

`avrt` нужен для MMCSS: он поднимает приоритет потока вывода, иначе
планировщик способен отобрать квант посреди подготовки буфера. CLSID и
IID интерфейсов WASAPI определены в самом модуле — ни одна библиотека
Windows SDK их не содержит.

У `liblaiue_audio.so` в зависимостях только `libc`; ALSA находится только в
отдельном `liblaiue_audio_output.so` и загружается в рантайме. Так SDK может
удалить output provider на машине без звуковой подсистемы, не ломая микшер.
